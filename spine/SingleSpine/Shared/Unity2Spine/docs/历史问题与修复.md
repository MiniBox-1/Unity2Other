## 1. 几何/姿态类（早期三大问题）

| 现象 | 根因 | 修法 | 数字 |
| --- | --- | --- | --- |
| 面罩/部件朝向、镜像反复错 | 世界矩阵写成 `T·S·R`（Unity 是 `T·R·S`，按列缩放） | `unity_anim2d.trs_mat` 改对顺序 | 三主力逐顶点误差 **aeda 0.00001 / blacklilith 0.00000 / audrey ≤0.0012**（= 关键帧裁剪阈值级） |
| 运动中部件"分离/跟不上" | 蒙皮 blend 索引编码两种（整数 / float 位模式）只认一种 | 两种都解析 | 同上 |
| 同类部件被绑到"少了 (n) 后缀"的另一个节点 | 曲线 `path` 超长时 Unity 换行续写，只读了第一行 | `_read_path_field` 拼接续行 | — |
| 静态立绘 + 动态立绘"两张脸" | 双根 prefab 默认把整图也导出 | 默认只导 Animator 子树（`--animated-only`） | constantias2 系列修好 |
| **曲线整条丢失（表情/手不动）** | 打包过的 clip 把 path 换成 **`CRC32` 哈希**（`path_0x…`） | 新增 `path_hash/hashed_path_table/resolve_clip_paths`，四处 clip 加载点还原 | `alice_skin2` 显隐对账 **13 → 0**；50 角色里只有 2 个有哈希路径，还原后未解出 0；位姿曲线是 euler 的重复（世界坐标差 0） |

## 2. 图像/贴图类

| 现象 | 根因 | 修法 | 数字 |
| --- | --- | --- | --- |
| 头上/脸上"碎块"、腿肩灰白块 | sprite 用矩形/alpha 轮廓近似，把邻近图素也画了 | **直接读精灵资产里 Unity 生成的网格**（`m_RD`），轮廓只兜底 | banshee 20 个 sprite **全 `asset`**、17 个与 Unity 逐位相同；盖住的不透明像素 **39 454 → 0** |

### 2a. 为什么"同 `sortingOrder` 内"必须按层级 DFS 序（2026-09-17 晚补）

- Unity 透明件的排序键是 `(sortingLayer, m_SortingOrder, 到相机深度)`；
  2D 角色所有部件 z 基本相同（`_refshot_cerberus_skin3` 的 103 个渲染器里
  **101 个 camDepth = 10.000、2 个 10.002**）⇒ 同 `sortingOrder` 内深度并列，
  先后由**渲染器列表序**（`GetComponentsInChildren` 式层级深度优先）决定。
- 直接证据：`info/Data/PlayFrames/*.json` 的 `renderers` 数组**SpriteRenderer
  段内**与 prefab 层级 DFS 序逐项相同（`eye_1` 在 `eye_star1` **之前**）；
  Unity 截图也是星形瞳孔压在普通眼之上，而文件序恰好相反 ⇒ 文件序必错。
  ⚠️ 该数组是"SMR 段 + Sprite 段"两段拼接，只有段内顺序有意义。

### 2b. spine-cpp 3.8 的 `.atlas` 越界读（2026-09-17 晚）

| 现象 | 根因 | 修法 | 数字 |
| --- | --- | --- | --- |
| `beasthunter_skin1` "动不了"、`blacklilith_skin2` 一打开就崩（`0xC0000005`，加载期） | **多页 atlas 文件正好在最后一行属性处 EOF（没有尾换行）** ⇒ spine-cpp 3.8 解析越界读 | `spine_out.atlas_text()` 末尾补 `"\n"` | 原样 416 B **崩**；+`\n`/空格/`\r\n`/`\0`（417~419 B）都不崩；砍 1 字节（415 B）也不崩。50 个产物里多页 atlas 只有这 2 个，修完重导都 OK |

## 3. 显隐/颜色类（最反复的一类，**结论看最后一行**）

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 圆环/针/骨骼标记画在身上 | 编辑器助手贴图（`m_Enabled=0` 的 gizmo 件）被导出 | 无 `m_Enabled` 曲线时回落静态 `enabled`；再加 `--skip-texture` 屏蔽表 + `excludedParts` 记账 |
| 特效部件显隐整条丢失 | 副 Animator 的 `m_IsActive` 曲线 path 基准错（相对它自己的宿主） | 按宿主重算 path（**不能用全局后缀匹配**，会极性反转） |
| 互补表情"同时 ON" / 该显示的"消失" | `m_IsActive` 的求值口径 | **最终口径**：按切线**插值** + `|v|>1e-3`（反汇编 + 同版本实测），再叠加**正确的 alpha 时间轴** |
| 部件整段半透明 | 颜色时间轴去重把"保持段"吃掉了 | 改成"**共线才丢**"：16 角色 179 条曲线里 129 条命中，最大偏差 0.98 → ≤0.002 |
| "两张脸 / 多口 / 多手"整类 | 一部分是**真值陷阱**（见下），一部分是绘制顺序 | 先用 `truth_chain_probe` + 场景体检排掉假问题 |

> ⚠️ **改了又被推翻的那次**：2026-09-16 夜一度把口径改成"阶跃 + `v≥0.5`"
> （当时看到"多口同时在"，怀疑是插值惹的祸）。用 7 角色 × 3 状态 × 10 时刻的
> **Play 参考帧**复核后发现：运行时确实是插值口径，改成阶跃会**整段藏掉**
> draculina 181 处 / banshee 57 处（心形瞳孔、腮红、手臂阴影等只在插值窗口出现）。
> 现在 `USE_RUNTIME_ACTIVE=True` 是定稿，`--active-step` 只用于对账。

> ⚠️ **第二次被推翻（2026-09-17 晚，同一个坑要先看这里）**：
> 傍晚把"同 `sortingOrder` 内次序"从文件序改成**层级 DFS 升序**（`hierarchy_ranks` /
> `slot_key_with_rank`）。当晚用新写的 `Assets\Editor\ExportDrawOrder.cs`
> （成对隔离渲染实测"谁盖谁"）在 `cerberus_skin1` + `banshee_skin1` 上一测：
> **7 条可用实测关系 7/7 与"升序"相反、7/7 与"降序"一致**（例如
> `parts_eye_1` 盖 `parts_eye_sleep` 70:0 票、`parts_Eye_normal` 盖
> `parts_Eye_Sleep` 85:0 票）。
> 当晚继续查：反汇编（`UP2022.dll`，见 `docs\渲染顺序_反汇编研究.md`）拿到 Unity 的
> 比较器 —— 第一顺位是包裹"层+顺序"的 `GlobalLayeringData`，然后才是深度、
> `CompareSortingGroupData`、稳定化字段；并用**反射读出内部属性 `Renderer.sortingKey`**
> 做实测：`(sortingKey, 深度)` **100% 解释 5,012 条非并列关系（0 反例）**，
> 43 条真并列里 36 条支持"**同值内 DFS 序小的画在上面**"。
> **最终规则 = `(sortingOrder, 同值内 −DFS序)`**（`slot_key_with_rank` 里 `rank → -rank`），
> `cerberus_skin1` 重导后眼睛从"半闭"变成 **睁眼**，与 Unity 帧一致。
> 教训：**先实测（特别是拿 Unity 自己的 key）再改公共代码**。

## 6. 真值/工具类（"看着像 bug，其实是我们判据错了"）

| 现象 | 真相 |
| --- | --- |
| `ModelInspect` 的 `dynamic.json` 里显隐不随动画变 | 它不能当显隐真值（17 帧 0 变化） |
| `ModelInspect` 的 `meshMin/meshMax` 比真值小 6 倍 | 工具口径 bug（少乘一层世界缩放），已修；对账请用 `boundsCenter/boundsSize` |
| `calib_geo` 报某部件 0.26 的假误差（alice_skin1_fix 的 `parts_curtain`） | 同一个 controller 的**第二层**驱动的部件混进了单 clip 比对 ⇒ 加"整层排除" |
| 一堆"Unity 显示/我们隐藏" | 参考帧来自**场景实例**，场景里的显隐被改过（draculina 10 个节点、constantias2 `face`） |
| `xxx t=0` 普遍对不上 | 状态首帧混着进入 Play 的过渡；PoseFrames 的 t=0 甚至没应用 pose |
| `ExportDrawOrder` 一次导出 60 目标全是空帧（`enabled=true` 0 个、`实测对 0`、PNG 白底） | `Names="*"` 曾把**角色内部的子物体**（`size_root`/`ch_root`/`bone_*_wing`…）也当独立目标；导出真角色时把"其它目标"（=它自己的子节点）整根 `SetActive(false)` 了 ⇒ 零可见渲染器。修法：`*` 只取"候选集合的根"，关其它目标时跳过有父子关系的；另加"可见渲染器 0 个"的安全网日志 |
| 同上，修完嵌套后**还是**空帧（`activeInHierarchy=True` 但 `enabled=true` 0 个） | 这批角色在场景里是 **Renderer 级 disabled**（`m_Enabled=0`，游戏运行时按需开）；只 `SetActive(true)` 不会改 `Renderer.enabled`。修法：新增 `ForceEnableRenderers` —— 采样每帧临时 `enabled=true`（记原值、帧末还原），同一段同步代码里强制，脚本抢不过 |
| 产物目录互相覆盖（`_draworder_size_root` 被 5 个角色轮流写） | 场景里有多个角色的**子节点同名**（`size_root`/`ch_root`…）。修法：目录名/标签改成"从场景根到目标的完整路径"（`__` 连接），顶层角色名不变 |
| 采出来的画面**和直接 PlayMode 打开不一致**（用户反馈） | 脚本"制造"了游戏不会出现的状态：自己 `SetActive` + 强开 `Renderer.enabled` + 关掉别的角色。修法：默认 `TouchMode="observe"` —— **一个字节都不改场景**，每帧等游戏自己把角色显示出来（根 active 且有 enabled 渲染器）再采，顺序由游戏决定；主帧不隔离（`IsolateFrame=false`），只有成对隔离判定才临时关别的角色并立刻还原 |
| **排序模型本身在 20% 的对上被实测推翻**（101,520 条强证据：52,925 对 / **17,794 反** / 363 真并列） | 层全是 Default、材质队列全是 3000、也不是 sprite/mesh 通路差异 ⇒ 去反汇编查 Unity 真正的比较键：`RenderObjectSorter` @0x180440CC5 依次比 `u32(层+顺序) → u16(renderQueue) → float(深度) → CompareSortingGroupData`，且 `renderQueue ≤2500` 与 `>2500` 是**两套列表分开排、分开画**。详见 [`渲染顺序_反汇编研究.md`](渲染顺序_反汇编研究.md)；下一步用反射导 `Renderer.sortingKey` 定案 |
| 深目标产物写文件失败（`DirectoryNotFoundException`） | 目标标签用了"完整层级路径"，撞上 Windows 260 字符限制（`bloodypanther...__BR_BloodyPanther_NS1_Back__n0050_cam.txt`）。修法：标签太长时退化成"首段+末段+散列"，tag 整体压到 80 字符内 |
| **校验器假报"2 个 slot 时序差"（bheur）** | 校验器只读 `m_IsActive`，**没读 `m_Enabled`**；而部件可见 = 两个开关都为真。Unity 源文件里 `Part_Eye_Close_R` 的 `m_Enabled` **0.13333 就关**、`m_IsActive` 到 0.45 ⇒ 真实窗口 [0,0.133]（转换器一直是对的）。修：校验器也读 `m_Enabled`（`#enabled` 后缀一起 AND）+ **共用** `ACTIVE_DEAD_BY_ROLE` 例外表 ⇒ 50/50 全绿 |
| 用户报的"banshee 手"、"constantias2 镜像" | 都是**参考数据/观感问题**：banshee 手部几何与真值差 0.003~0.004（唯一 0.1 的件是参考帧 `verts` 里 6/10 帧 NaN）；constantias2 全部件"直接贴合"比"镜像贴合"近 10 倍 ⇒ 无镜像 |

## 8. 2026-09-18：`m_Bones` 全空 = Unity 画不出来（"飘头发 / 表情重叠"）

用户第 3 批里的 3 条（`constantias2_normal` 头发飘在外面、`constantias2_skin1S`
头发飘在外面、`cerberus_skin3` 表情重叠严重）是**同一个根因**。

**现象**

* constantias2 系列：角色右上方的空白处**多出一缕头发**（我们画、Unity 不画）。
* cerberus_skin3：脸上**闭眼/笑眼叠在睁眼上**（"表情重叠严重"）。

**怎么定住的（这一步可当模板）**

1. 新写了 `_scratch\truth_diag.py`：把我们的渲染按**相机精度**贴到
   `_draworder_*`的参考帧上（`_static_info.json` 的 unitScale/origin +
   setup 包围盒 → 世界 → `_cam.txt` 的 cx/cy/ppu），然后
   **逐渲染器**（真值的 `screenBox`）算差分，还能给出"差>48 的连通块"落在谁身上。
   两个坑：真值 PNG 的 y 与 `screenBox` 的 y 是**反的**；我们的 `--size` 是
   正方形视口，映射要用 `(ours,ours)` 而不是相机 w/h。
2. 对账结果：`constantias2_normal` 20 帧（4 clip × 5 时刻）里，
   `CS_parts_hair_3`(order=−3) 的框内**真值墨迹恒为 0**，我们却画 1237 px；
   `cerberus_skin3` 的 4 个眼部件框内**平均差 29~48**（全图 4.0），
   `Part_Eye_Smile_R` 与 `Part_Eye_Close_R` 还占**同一个框**
   `[432,162,481,193]` —— 正是"两层表情叠在一起"。
3. 回源数据一看：这 5 个渲染器的 `m_Bones` **非空但全是 `{fileID: 0}`**

### 9.2 算法差异 B：**逐帧排序（`m_SortingOrder` 可动画）没有进产物**

> **进展（2026-09-18 17:4x）**：已把 `draw_order_timeline()` **接回**导出流程
> （`static_prefab_spine.py` 写动画处，紧接 deform 之后：算出逐帧目标顺序 →

> 它按"setup 序号升序 + 非负偏移"压缩，能精确表达的帧必须满足

> 再统计有多少帧变得可表达；仍不可表达的再退回 `--multi-drawable`（一部件多槽位 +

## 10. 2026-09-18 晚：banshee 手的**真根因**——同网格多渲染器的**骨骼表不一致**

> ⚠️ **勘误**：第 9.6 节 / `渲染顺序_反汇编研究.md` 6c 里"**父子对并列顺序要反过来**"

### 10.1 现象与真值

* 现象（用户）：`banshee_skin1` lobby，手腕处**一条硬边黑线**、**手指下面看不到手心**、
  **明显多一块**；换位置（父件画在前面/后面）都不解决。
* 真值来源：`info\Data\PoseFrames\<角色>@<clip>.json` 的 **`frames[i].skinned[]`**，
  其中 **`positions` 是"蒙皮后的局部顶点"**（`localToWorld` 一转就是世界坐标）。
  ⚠️ 这跟第 9.3 节写的"`positions` 是局部顶点、不随动画变"**相反**：实测
  `positions` 与 mesh 原始顶点不同、且逐帧变；拿它当蒙皮真值，**40 个件里 39 个差 0.0000**
  （工具：`_scratch\pose_check.py <产物> <PoseFrames json> <动画> <归一化时刻>`）。

### 10.2 根因（算法）

两个 `parts_Hand_R` 是**同名父子**、**共用同一份网格**（`Mesh/parts_Hand_R.asset`，
4 个 bindpose），但**骨骼表不一样**：

| 渲染器 | `m_Bones` |
| --- | --- |
| 父（`…/Global_CTRL/parts/parts_Hand_R`） | `Bone_Hand_R, Bone_Forearm_R, Bone_Finger_R1`（3 根） |
| 子（`…/parts_Hand_R/parts_Hand_R`） | `Bone_Hand_R, Bone_Forearm_R, **Bone_Hand_R+**, Bone_Finger_R1`（4 根） |

网格的顶点权重用的是 **bindpose 槽位**（v19~v22 还会用到槽 3），我们按
"**第 k 个权重索引 → `m_Bones[k]`**"配对：父件的槽 2 被对到 `Bone_Finger_R1`
（权重 0.6~0.81！），于是整块被撑成另一形状 ⇒ 盖住手心、边缘成"硬黑线"。

Unity 侧不是这么配的：`SkinnedMeshRendererManager::CalculateSkinningMatrices`
（`0x180528240`）用的是**两组索引表**（`[entry+0x30]`=bindpose 下标、`[entry+0x38]`=骨骼下标），
即"**槽位 → bindpose / 骨骼**"的**重映射**，不是按 `m_Bones` 的下标硬配；
真值也证实：父件与子件在 Unity 里**同一个形状**（世界张成 0.219×0.085）。

### 10.3 修法（通用，不加角色名单）

`src\unity2spine\convert\convert_2dmodel.py`（`build_character_model` 末尾）：
**同一份网格被多个 `SkinnedMeshRenderer` 共用、而骨骼表长度不一致时，用"最长的那份
骨骼表"**（= 网格 bindpose 数的那份，正是 Unity 蒙皮数据按网格缓存的口径）。
长度本来就一致的部件**完全不受影响**（audrey 回归：几何逐件不变、`static_check` 四项 0）。

日志会打一行：`[skin] 同一网格的骨骼表按最长的共享 N 个部件：…`。

* banshee：父件误差 **0.2526 → 0.0323**（≈22 源像素的常量偏移，见 10.4），
  `check_clip_visibility` 4 条动画 **0 个 slot**，渲染同帧对照**硬楔形消失**、与 Unity 同形。
* 全 50 个里还会命中 audrey 等（日志能看到），**几何与数值都不变**。

### 10.4 已知残留（记进 `现状与问题.md`）

父件还剩 **0.032 世界单位（≈22 源像素）的常量偏移** = Unity 里父件与子件的世界位置差。
原因：Unity 的蒙皮还会乘一个"基础矩阵"（`MultiplyMatrixArrayWithBase4x4(a3, a5, a4, …)`，

### 14.3 结论：**副层该并，我们的产物是对的** —— 证据链

1. **资产**：`BR_Bheur_NS1.controller` 里 `Drone` 层 `m_BlendingMode: 1`（Additive）、
   `m_DefaultWeight: 1`；它的状态机 **有默认状态** `2DModel_BR_Bheur_NS1_Drone`
   （`m_DefaultState` 指得到），该 clip `m_LoopTime: 1`、时长 **3.3333 s**。
   （`Base Layer` 写 `m_DefaultWeight: 0` 是**假象**：Unity 里第 0 层的权重恒为 1，
   编辑器里那个框是灰的；`alice_skin2` 的 `Face` 层才是真的 0 ⇒ 我们不并它，正确。）
2. **游戏代码**：全工程 `Assets\Script` / `OnShowing` 里**没有任何** `SetLayerWeight`，
   而且游戏只调 `animator.Play(stateName)`（单参数 = 只播第 0 层）⇒ 副层没人关，
   它以权重 1 从头开始循环播。
3. **运行时实测**（新 `layers[]`）：`bheur`/`blackwyrm`/`circe` 三角色的副层权重全是 **1**。
4. **轨迹比对**：把产物的 `2DModel_BR_Bheur_NS1_Drone` 动画按 drone clip 的真实周期
   （3.3333 s）取样，与 observe 真值里**直接把 drone 状态播出来**的那 5 帧
   （`_draworder_bheur_skin1__…__2DModel_BR_Bheur_NS1_Drone__n00xx`）比：
   5 个相位上两个 drone 件的差是 **0.010~0.016**，而且**不随时间增长**（常量偏置 = 两边
   基础姿势不同），drone 自己的位移幅度 ~0.07 完全对得上 ⇒ **产物的 drone 就是那个 clip 的动**。
5. 那"真值里 drone 完全静止"是怎么来的？**所有采样器都 `Rebind()` 后再拍**：
   `Rebind` 会把副层退回它的默认状态、并且**没人推进时间**，所以副层永远停在
   `normalizedTime = 0`（新 `layers[]` 里写得明明白白：`weight=1, normalizedTime=0`）。
   于是真值里的 drone = "drone clip 的 t=0 姿势"= 恒定 ⇒ 拿它判"我们多动了"必然误判。
   **这和 13.1 里 `babariana 2→4` 是同一类坑**（那次是 PoseFrames 只驱动一台 Animator）。
6. 副产品：那个 0.086/0.066「随 t 单调增大」也是老口径造成的——老帧比标称时刻晚 2~3 帧，
   等于拿"drone 在 t+0.05 s 的位置"跟"我们 t 时刻的位置"比。改完口径后，同样的比较
   在 t=0.5/1.5/2.5 上是 0.074 / 0.026 / 0.150（= drone clip 自身走到哪儿了）。

**所以 `static_prefab_spine.py` 的副层合并规则不动**（`weight==1` 才并；Additive 用
`base + (over(t) − over(0))`，Override 直接覆盖；over 按自己的时长循环）。

### 14.6 遗留（已知、可接受，别再当 bug 追）

副层有**自己的时钟**：游戏里那个 drone clip 从角色出现那一刻开始循环（3.3333 s 一圈），

所以"玩家站着不动看 10 秒"这种场景里，两边的 drone 相位会慢慢错开——**这是表达能力问题，
不是几何错**（Spine 一条动画装不下两个独立时钟）。要更贴近就得把 drone 拆成独立动画/独立

### 14.7 查这轮时又踩到一个真值坑（已记 2.0b **T**）

circe 的 drone 因此只能**结构性判定**：它的 Drone clip（13.0333 s、`m_LoopTime:1`）
