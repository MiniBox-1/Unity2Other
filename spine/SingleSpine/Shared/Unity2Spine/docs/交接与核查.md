## 2. 可用的技术手段（核查时按这个顺序挑）

### 2.1 ⭐ 用 **C# 脚本导出 Unity 运行时数据**（拿"真值"）

Unity 工程 `Assets\Editor\` 下两个现成脚本，**Play 模式、菜单一键、参数硬编码**：

| 脚本 | 导什么 | 入口 |
| --- | --- | --- |
| `PlayRefShot.cs` | **参考帧**：PNG + 相机参数（`_cam.txt`）+ **同帧逐渲染器数据**（路径 / `activeSelf`/`activeInHierarchy`/`enabled` / `sortingOrder` / `boundsCenter` / `camDepth` / **世界顶点 `mesh.verts`**） | 菜单 `Tools/2DModel/运行时采样/参考帧（带相机）…`；参数在 `PlayRefShotPlan` |
| `ExportDrawOrder.cs` | **渲染顺序**：每渲染器的排序键 + **反射读到的 `Renderer.sortingKey`** + **成对隔离渲染实测的"谁盖谁"**（`PairScope="tie"/"all"`） | 菜单 `Tools/2DModel/运行时采样/渲染顺序导出：按内置清单开始`；参数在 `ExportDrawOrderPlan` |

要点（都是踩出来的）：

* **必须 Play 模式**（`-batchmode` 进不了 Play）；日志 `D:\VB\Unity2Spine\info\_logs\play_sample.log`。
* **所有动态导出统一写在 `D:\VB\Unity2Spine\info`**：`info\_refshot_<角色>\`、
  `info\_draworder_<角色>\`、`info\Data\{PoseFrames,PlayFrames,Frames,SceneT0,…}`、
  `info\_logs\`；开关只有 `Assets\Script\ExportRoots.cs` 的 `ExportRoots.Root`。
  逐步怎么导（含"场景里只有一台原始照相机"）见 [`导出指南_Unity运行时数据.md`](导出指南_Unity运行时数据.md)。
* `ExportDrawOrder` 默认 `TouchMode="observe"`：**一个字节都不改场景**，等游戏自己把
  角色显示出来再采（画面 = 直接 Play 的样子）；`force` 才是脚本激活 + 强开渲染器。
  它还会在**退出 Play 时自动停**并还原现场。
* 读结果：`python tools\read_draworder.py <目录>`（并列组实测顺序 vs DFS 序、
  全局逆序对）；`tools\check_draworder_rule.py`（哪条排序规则能完全解释实测）。
* 真值也要**体检**（第 4 节）：场景实例可能被改过、`t=0` 没应用 pose、
  某些渲染器的 `mesh.verts` 会出现 **NaN**（实测 10 帧里 6 帧）。

### 2.2 ⭐ 用 **反汇编（IDA）做源码校对**（拿"引擎真实行为"）

Unity 没源码，但引擎算法能从 DLL 里读出来，用来给我们的实现对表：

| 东西 | 路径 |
| --- | --- |
| 库 | `_reverse\UP2022.dll.i64`（IDA 8.3 数据库，221 MB；`UP2022.pdb` 同目录） |
| 查询器 | `tools\ida_q.py` —— `info / names / strings / xrefs_to / disasm / decompile / funcs_at / calls / bytes_at` |
| 跑法 | `idat64.exe -A -L"_reverse\ida_q.log" -S"tools\ida_q.py" "_reverse\UP2022.dll.i64"`（请求写 `_reverse\req_*.json`，结果 `res_*.json`；`REQ_INLINE` 可一次跑多条） |

**坑**：多数符号地址是**跳转桩**，`decompile` 出 `JUMPOUT(x)` 时要用 `x`（约 `ea+3`）
再解一次；跑完 `Get-Process idat64 | Stop-Process -Force` 收进程（221 MB 的库很占内存）。

已经用这条手段定过的（可当模板照抄）：

| 结论 | 地址 / 符号 |
| --- | --- |
| 前向渲染**排序比较键**顺序：`u32(层+顺序) → u16(renderQueue) → float(深度) → CompareSortingGroupData → …` | `ForwardShaderRenderLoop::RenderObjectSorter<0>::operator()` @ `0x180440CC5` |
| `renderQueue ≤2500 / >2500` 是**两套列表分开排、分开画** | `BuildRenderObjectData` @ `0x18042D1A3` |
| C# 侧 `Renderer.sortingKey` 的原生绑定（用来反射读真值） | `Renderer_Get_Custom_PropSortingKey` @ `0x1800A6960` |
| 显隐口径（`SetBoundCurveFloatValue` 的 case 编号：6=Enabled、10=SortingOrder…） | 见 `_archive_20260917\Unity运行时逆向报告.md` |
| 精灵轮廓兜底算法 | `SpriteUtility::GenerateSpriteOutline` |

### 2.3 四层校验闭环（每次改完都跑）

| 层 | 工具 | 判据 | 能发现什么 |
| --- | --- | --- | --- |
| ① 结构 | `python tools\static_check.py <prefab> --assets <A> --spine-dir <产物>` | 四项**全 0** | 曲线引用了却没导出、静态可见没导出、与真值可见性冲突、曲线 path 对不上 |
| ② 几何 | `python tools\calib_geo.py --prefab … --pose … --only-spine-dir --spine-dir <产物>` | 逐顶点世界误差（三主力 ≤0.002） | 姿态/镜像/尺度错 |
| ③ 显隐 | `python tools\check_clip_visibility.py --spine-root _probe50_rt4 <角色…>`（对 clip）／`check_play_visibility.py`（对 Play 真值） | 逐槽位时间轴一致 | 该显示的没显示 / 两个表情同时出现 |
| ④ 观感 | `tools\rt_frames.py` 出帧 + `_scratch\cmp_truth.py` 同帧并排 | 差异只剩边缘抗锯齿 | **"谁盖谁"、绘制顺序**（前三层看不出来） |

> ④ 的更省事入口：**`python _scratch\truth_diag.py --spine-dir <产物> --anim <动画>
> --truth-dir info\_draworder_<角色> --ours-dir <rt_frames 输出> --out <差分目录>`**
> —— 自动按相机参数对齐，**逐渲染器**给差分，并列出"差>48 的连通块"最可能是哪个件
> （`--times 0.05,0.25` 对应真值 `n0050/n0250`）。配套 `_scratch\variant_probe.py`
> （隐藏/清零某个 slot 做对照实验）、`_scratch\cmp_product.py`（两份产物按 path 对账）。

### 2.4 逐部件世界顶点对账（离线、不渲染、最省内存）

拿参考帧 JSON 里的 `mesh.verts`（世界坐标）和我们同一时刻算出来的顶点比**最近邻距离**，
一眼看出是**几何错**还是**显隐/顺序错**（脚本思路见 `_scratch\q5_mirror_check.py`）：

| 观察 | 含义 |
| --- | --- |
| 平均差 0.003~0.006 世界单位 | 几何对得上（banshee 手就是这个结论） |
| 某个件差 0.1+ 而其余件正常 | 先怀疑**该件自己的曲线没绑上**（同名孪生/哈希路径） |
| 直接贴合比"镜像贴合"还差 | 才是**镜像**问题（constantias2 判过：无镜像） |
| 参考帧里该件 `verts` 出现 NaN/跳到局部坐标 | **参考数据坏了**，换帧再判 |

## 3. 一条问题从报告到闭环（标准 6 步）

1. **确认看的是最新产物**：`_probe50_rt4\<角色>\` 时间戳应是重导之后，且
   `.json`/`.skel` **同时**存在。查看器优先读 `.skel` —— 只更新 JSON 不重写 `.skel`
   画面不会变（`python tools\write_all_skel.py _probe50_rt4 --force`）。
2. **复现**：`rt_frames.py` 出同动画同时刻的帧；与用户截图/Unity 参考帧对齐。
3. **定性**：按第 2.6 节决策树挑手段；先离线（2.4）后渲染，先便宜后贵。
4. **定位到根因**：要么是我们的数据（切静态资源 → 改转换器），要么是**真值陷阱**
   （场景实例被改过 / t=0 / 孪生节点 / NaN）——两者结论都要写进文档。
5. **改 + 单角色回归**：动公共代码只挑**一个主力角色**（audrey）跑四层里的①②③，
   必要时加④；要求"四项全 0 + 逐字节一致（或差异可解释）"。
6. **写回文档**：现象 → 证据（数字）→ 根因 → 修法 → 影响面，进
   [`历史问题与修复.md`](历史问题与修复.md)，状态改 [`现状与问题.md`](现状与问题.md)。

## 4. 铁律与坑（违反过的都出过事）

1. **只用磁盘静态资源**转；Unity 导出的参考数据**只做校准，不进成品**。
2. **内存**：本机 15.8 GB；重活前用 `tools\mem_probe.ps1` 量**进程树峰值**，
   同时跑的峰值之和 ≤ 10 GB。具体坑：
   * 大产物走 **JSON 路径 >11.6 GB**，走 `.skel` 0.6~0.8 GB（`draculina` 的 JSON 实测 **10.5 GB**）
     ⇒ **大产物必须有 `.skel`，别直接读 JSON**；
   * 连续加载骨架的审计脚本会**线性泄漏**（25 个角色 10.3 GB）⇒ `--max 5` 分片；
   * Unity 批处理 ≈1.84 GB，**同时只跑一个**，绝不与渲染/转换并行。
3. **看图片用多模态**（或先 `_scratch\crop_zoom.py` 裁切放大），不要用文本读图。
4. **改完只回归一个主力角色**（默认 audrey），别顺手全量重导。
5. **真值先体检**（第 1 节 2.1 的四条）：场景≠prefab、别采超 clip 时长、
   别信状态第一帧、`PoseFrames` 的 `t=0` 可能没应用 pose；`ModelInspect.dynamic.json`
   不能当显隐真值；同名孪生节点要让"同一路径有没有任一可见"。
6. **Windows 文件名**别按完整层级路径拼（260 限制，深目标写文件会失败）。
7. **反汇编**记得跳转桩 `+3`、跑完收 `idat64`。
8. **PowerShell 脚本注释只用 ASCII**（PS 5.1 按 ANSI 读，中文会把脚本读坏）。
9. **先怀疑真值，再怀疑产物**：判断"谁对"之前，先确认这份真值本身没坏
   （下面 4.2 的四条都是"真值/工具口径坏掉 ⇒ 判出假 bug"）。

### 4.3 已定案的算法规则（18 条，改代码前先对一遍）

> 这些规则每一条都是"被真值或实测逼出来"的，细节与数字见
> [`历史问题与修复.md`](历史问题与修复.md)；旧详版在
> [`_archive_20260919/总正确转化.md`](_archive_20260919/总正确转化.md)。

1. 世界矩阵 `M = T·R·S`（按列缩放）——写成 `T·S·R` 会让非均匀缩放件朝向全错
2. 蒙皮 blend 索引两种编码（整数 / float 位模式）都要认
3. 曲线 `path` 折行要拼回去（超长路径 Unity 会续行）
4. `path_0x…` **哈希路径**要还原（= CRC32(相对宿主路径)），否则整条曲线丢
5. Sprite 的网格**直接读精灵资产**（`m_RD`），alpha 轮廓只兜底
6. 多材质网格按 **submesh** 拆
7. 没有 `m_Enabled` 曲线时回落渲染器**静态** `enabled`
8. 显隐按**运行时口径**：插值 + `|v|>1e-3`（不是 `v≥0.5`）
9. 颜色时间轴**共线才丢帧**
10. 一个 controller 挂两个 Animator 时按 `(controller,state)` 去重
11. 副 Animator 的 path 相对**它自己**的宿主；**副层的默认 clip 要合并**
    （`weight==1` 才并；Additive 用 `base+(over(t)−over(0))`，Override 直接覆盖，
    over 按自己的时长循环；`alice_skin2` 的 `Face` 层权重 0 ⇒ 不并）
12. **绘制顺序 = `(sortingOrder, 同值内 −DFS序)`**（反射读 `Renderer.sortingKey` 实测，
    5,012 条非并列关系 100% 解释）
13. 同 order 内"相对层级会变"才需要多 drawable；默认关（实测否掉，见 13.2）
14. 大产物必须同时写 `.skel`
15. `.atlas` 末尾要有一个换行（否则多页 atlas 会让 spine-cpp 越界读崩）
16. **`m_Bones` 非空但全是空引用的 SMR，Unity 一个像素都不画** ⇒ 必须排除；
    ⚠️ `m_Bones: []`（空列表）**不在**此列（arman 的眼镜就是空列表且正常）
17. **同名孪生节点，曲线只绑"第一个"**（节点表加"同名序号"）
18. **`m_SortingOrder` 是可动画属性** ⇒ 逐帧顺序要写成 Spine 3.8 的 `drawOrder` 时间轴
