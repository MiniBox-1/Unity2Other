## 1. 目标与动机

现路线是"**1 根 `Root` 骨 + 每部件一个 mesh + 逐帧逐顶点 deform**"：一条动画的体积 ∝ **顶点×帧**，
和动作复杂度无关，50 个角色 JSON 3.1 GB。

换成"**真骨骼树 + 加权 mesh**"后，体积 ∝ **骨×关键帧**，而且 Spine 会插值，**可以抽稀**：

| 表示（`cerberus_skin1` lobby，2026-09-17 实测） | JSON |
| --- | --- |
| 现状：单根骨 + 逐帧逐顶点 deform | 5.45 MB |
| 真骨骼树，不抽稀 | 4.82 MB |
| 真骨骼树，骨键抽稀 0.5 / 2 / 5 单位 | **0.48 / 0.31 / 0.24 MB** |

⇒ 抽稀后是现状的 **1/11 ~ 1/23**。粗估整个 `_probe50_rt4`（JSON 3.14 GB）能落到 **0.2~0.6 GB**。

## 2. 本轮修掉的三个真 bug（都有硬依据）

### 2.1 加权 mesh 用错了格式（上一轮"一加载就崩"的根因）

旧原型把 `vertices` 写成 **spine 4.x 的 `[x, y, w0, w1 …]`**；而 **3.8** 的解析器要的是**打包布局**：

```text
vertices = [boneCount, (骨下标, 该骨局部 x, y, 权重), …]      # 每顶点一组
```

**依据**：`_reference/SpineSkeletonDataConverter/spine38/SkeletonJson.cpp:1182 SkeletonJson::readVertices`
—— `verticesLength == len(uvs)` 时按**无权**读，否则按上面的打包格式读。
又用**官方 3.8 样例**核对了口径：`D:\VB\Viewer\Render\_testdata\Spine\380_spineboy\export\spineboy-pro.json`
（spine 3.8.55）—— 骨下标是**骨架 bones 的下标**、每组 `(x,y)` 是**该骨局部坐标**
（新工具 `_scratch\check_spine38_weighted.py` 把每个影响点还原到骨架空间，官方样例 head/torso 误差 ≤0.06 px）。

> 症状对照：格式错 ⇒ spine 把 `x` 当 `boneCount` 越界读 ⇒ **连"4 顶点 1 骨"的最小 quad 都崩**。

### 2.2 "顶点组少写一组" ⇒ 越界读

实现里一度在"该顶点没有有效影响点"时 `continue` 跳过顶点，而 `uvs` 仍然给它留了 2 个数
⇒ `worldVerticesLength(=len(uvs)/2)` 大于实际顶点组数 ⇒ spine 越界读（症状：**塌成一团 / 内存暴涨**）。

**修法**：每个顶点**必须**写出至少一组 `(骨, x, y, 权重)`（没有有效影响点就挂宿主骨）。
**自检**：78 个加权件的"组数 vs `len(uvs)/2`"**全部匹配**。

### 2.3 "渲染器宿主"节点不能当骨

这批 2D 立绘的 `parts_*` 宿主节点带 **离面旋转**或 **零缩放**：

| 例子 | 实测 |
| --- | --- |
| `parts_Body` | 四元数 (0, 0.7071, 0.7071, 0) = **绕 X 轴 90°** ⇒ 2D 分解出 `scaleY = 0` |
| `Size_root` | 绕 Y 轴 180° |
| `parts_Finger_R5` | `scaleY = -0` |

骨只能用 `(x, y, rotation, scaleX, scaleY)` 表达**平面内**变换 ⇒ 一旦把这些节点当骨，
**整棵子树被压成一个点**。Unity 里它们无所谓（蒙皮件的几何只由 `m_Bones` 决定，与宿主节点无关）。

**修法**：只把**蒙皮骨骼（`m_Bones`）及其祖先**当骨（且要求"平面内 + 非退化"），
部件（slot）挂到**离它最近的骨**上；顶点按 **3D 世界坐标**反解到那根骨的局部空间
（与 deform 路线同口径）。骨数 **200 → 156，退化骨 0 根**。

**已否掉的相关假设**：`_scratch\bones_ancestor_check.py` 复核"保留骨的父链上是否有被剔除的节点"
⇒ **156 根里 0 根**（不是它）。

## 4. 三条"会让查看器直接崩/错"的硬约束（踩过，别忘）

1. **`hull ≤ 顶点数`**：手搓用例抄了源件的 `hull=60` 却只填 4 个顶点 ⇒ **`0xC0000005`**。
2. **`path` 必须指向 atlas 里真实存在的 region**：漏写 `path` ⇒ region 查不到 ⇒ 空指针 ⇒ `0xC0000005`。
3. **动画通道只能引用存在的骨**：删了骨却留着它的 `translate/rotate/scale` 通道 ⇒ 崩。

（这三条正好解释了本轮前几次"最小用例崩"的**无效实验**，已在脚本注释里写明。）

## 7. 下一步（按成本排序）

1. **按链深度二分**（最关键、成本最低）：把同一个探针 quad 依次挂到
   `2DModel_BR_Banshee_NS1_root` → `Size_root` → `Global_CTRL` → `Bone_Pelvis` → `Bone_Spine1` …
   **第一根"挂上去就没墨迹/跑飞"的骨**就是查看器解释与我们不一致的那一层。
   重点怀疑**第一次出现镜像的那层**（`Size_root` 绕 Y 180°、`Global_CTRL` `scaleY=-1`）——
   真定位到之后，改 `convert_bones.py` 的局部 TRS 分解（可能要把"负缩放镜像"改成
   "旋转 + 顶点预镜像"，或按 Spine 的 `transform` 继承模式显式声明）。
2. **动画内存**：现在"156 根骨 × 4 条动画 × 最多 336 帧 × 三条通道"会把渲染器撑爆
   （单键 429 MB vs 全量 >2.5 GB）。落地要：**骨键抽稀**（原型 `--tolerance`）+ **只给真变化的通道写键**。
3. 骨骼层对齐后，再跑一遍"观感 + 四层校验"，并决定**是否把主转换器切到多骨骼路线**（动静很大）。
