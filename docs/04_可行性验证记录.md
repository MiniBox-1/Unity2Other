## E3 段语义标定（重要）

`calibrate.py` 把 py-moc3 读出的每一段与 Core 的真值数组逐一比对：

```text
core vc[:6]  [10, 47, 23, 23, 24, 21]   sum 1984
core idx[:6] [30, 210, 90, 87, 96, 57]  sum 7815
```

比对结果（Koharu，91 个 ArtMesh）：

| py-moc3 段名 | 实际内容 |
| --- | --- |
| `art_mesh.position_index_counts` | **顶点数**（10/47/23…，和 = 1984 = UV/2） |
| `art_mesh.vertex_counts` | **索引数**（30/210/90…，和 = 7815） |
| `art_mesh.uv_begin_indices` | 累计 `2 × 顶点数`（0, 20, 114, 160…） |
| `art_mesh.position_index_begin_indices` | 累计索引数（0, 30, 240, 330…） |
| `art_mesh.texture_indices` / `drawable_flags` | 与 Core 一致 ✅ |
| `draw_order_group_object.*` | 与 Core 的渲染顺序表一致 ✅ |

结论：
1. 公开库把「顶点数 / 索引数」两段**标反了**，但字节顺序是对的；
   写模型时按真实顺序填值即可；
2. 其它段（part / parameter / transform 类）没有发现错位；
3. `csmGetDrawableVertexCounts/IndexCounts/TextureIndices/GetRenderOrders`
   是最可靠的标定基准。

## E7 Y 约定 + begin 单位（E5 的未解释项，已定案）

`e5_y_axis.py` 用一个**不对称四边形**（四个顶点坐标互不相同）重跑：

```text
intended key0: [(-0.1,-0.3), (0.45,-0.2), (0.3,0.55), (-0.35,0.15)]

-- 按模型空间直接写入 --
key0: [(-0.1, 0.3), (0.45, 0.2), (0.3, -0.55), (-0.35, -0.15)]   ← Y 被整体取反

-- 写入时先对 Y 取反 --
key0: [(-0.1, -0.3), (0.45, -0.2), (0.3, 0.55), (-0.35, 0.15)]   ← 与模型空间一致 ✅
```

结论：

1. **moc3 的 keyform 顶点位置按 Y 取反存储**（`stored_y = -model_y`），
   X、顶点顺序都不变；读取时再翻回来。`build_min.py` 已按此约定写，
   读回与模型空间完全一致。
2. `keyform_position_begin_indices` 的单位是 **float 下标**（不是“位置对”）：
   用「block@8 = +0.3、block@16 = +0.2」的对照实验，读到的是 +0.3。
3. 上一版 E5 的“Y-0.1”其实是把偏移量 `+0.3` 错误地同时加到了 X 和 Y 上，
   再叠加第 1 条的 Y 取反造成的——两个自造错误，与 Core 无关。

**待验证（P1）**：rotation deformer 的 `origin_y`、warp deformer 网格点是否
同样按 Y 取反。实现时统一先在写入层做一次 `flip_y()`，再用 Core 读回断言。

## E6 画布与 ppu

- Koharu：canvas 1600×2000、ppu 1600、origin (800,1000)，顶点约
  x∈[-0.34,0.35]、y∈[-0.60,0.61]，即「模型单位 = 像素 / ppu」；
- E4 自选 ppu=1000、画布 1000×1000、顶点 ±0.25 也被 Core 接受；
- 结论：ppu 是自由参数，转换器可以按角色 AABB 自定，便于统一误差单位（px）。

**坑**：`csmReadCanvasInfo` 的 C 签名是
`(model, float* size[2], float* origin[2], float* ppu)`，
用 3 个独立 `byref` 传会踩内存；必须传**一段连续 5 个 float 的缓冲区**。
`probe_model.py` 里早期的错误读法就是这么来的（读出 1600×800 的假结果）。

## E8 keyform 排列顺序（多参数）

`tests\test_moc3_builder.py::test_two_params_axis_order` 用两个参数（各 2 键）
和 4 个位置不同的 keyform 做对角测试，结论：

```text
axes = [A, B]（A 在前）
(A=1, B=0) 命中第 1 个 keyform（index 1）
=> 第一个参数变化最快：index = iB * len(A) + iA
```

配套的 `Moc3Builder.grid_indices(axes)` 直接按这个顺序枚举组合：
`[(0,0), (1,0), (0,1), (1,1)]`。

## E9 渲染顺序（draw order group）

用 2/3/6 个 ArtMesh 做对照实验（Part 的 draw_order 与 ArtMesh 的 keyform
draw_order 分别扫）：

| 配置 | `csmGetRenderOrders` |
| --- | --- |
| 不输出 group | 全部 0 |
| group 的 min/max 取真实 draw order | 全部 0 |
| **group 的 min/max 固定 0/0** | 按 `draw_order_group_object.indices` 的位置给 0..n-1 |
| group 0/0 + indices 倒序 `[2,1,0]` | `[2,1,0]` |
| ArtMesh keyform draw_order ≠ 0 | 打乱/退化为 0 |

结论：

1. 输出 group，`min_draw_orders = max_draw_orders = 0`，
   `indices` 用**期望的前后顺序**（默认 ArtMesh 添加顺序）；
2. 也就是说，**moc3 v1 里我们可控的排序是“构造顺序”**，
   Part 的 `draw_order` 目前没有验证出对 render order 的影响；
3. 用真实 draw order 填 min/max 会让所有 render order 退化成 0 —— 这是坑；
4. 参数驱动的动态排序（sortingOrder 动画）暂时不要依赖 draw order，
   留到 P2 再标定。

## E10 变形器（Rotation / Warp）

`Moc3Builder` 加入两类变形器后，用 Core 读回实测：

| 用例 | 输入 | 读回 | 结论 |
| --- | --- | --- | --- |
| Rotation angle 0→90 | 顶点 (0.5,-0.1)… | (-0.1,-0.5)… | 正角度 = 顺时针，`(x,y)→(y,-x)` |
| Rotation origin (0.5,0) | 同上 | 整体 +0.5 X | `p' = R·S·p + origin` |
| Rotation scale 1→2 | 同上 | 顶点 ×2 | scale 作用在 origin 之前 |
| Rotation 90 + origin (0.5,0) | (0.5,-0.1) | (0.4,-0.5) | 证实是 `R·p + origin`，不是绕 origin 旋转 |
| Warp 1×1 网格 identity | 顶点 (0.25,0.25)… | 原样 | 网格点定义绝对位置 |
| Warp 网格 Y 拉到 2 | 同上 | (0.25,0.5)… | 双线性插值，**网格点不做 Y 取反** |
| 父子变形器 | 子平移 + 父旋转 | 先子后父 | 层级组合正确 |

配合 `docs\05` 的逆向结论（v<=5 头部 0x840、上下文 +704、SOT +64），
`src\unity2live2d\moc3\builder.py` 现在覆盖：Parts / ArtMesh / 参数 /
RotationDeformer / WarpDeformer / keyform 网格 / 纹理 / 排序。

## E12 骨骼链 → RotationDeformer + 参数（Alexandra）

`tools\build_alexandra_rigged.py`：74 根骨 → 74 个 RotationDeformer（父子链照抄
Unity 层级），每个骨一个参数 `P_<Bone>_Rz`（-30..30，3 个 keyform）。

| 项 | 结果 |
| --- | --- |
| 变形器 / 参数 | 74 / 74 |
| `csmHasMocConsistency` | **1** |
| 静止姿态逐顶点误差 | **5.84e-07** |
| 参数驱动 | `P_Bone_Head_Rz=30` 时马尾顶点从 (0.204,1.459) 移到 (0.354,1.367) ✅ |

过程中修掉三个真实 bug（都会让整条骨链算歪）：

1. **四元数只取 Z 分量是错的**：这批 prefab 的骨骼带 X 轴 180° 翻转，
   必须用完整 3×3 旋转取 XY 投影，否则 origin 会飞到 6+ 单位外；
2. **Live2D 角度正方向是顺时针**：`angle = -atan2(b, a)`，
   变形器矩阵是 `R(-angle)·scale·p + origin`，符号写反会让误差到 1.66；
3. 变形器必须挂在已存在的 Part 上（`parent_part_indices` 越界会让一致性直接失败）。

已知问题：**主导骨骼分配**。这批 SMR 的 `m_Bones` 表混了表情骨与手/臂骨
（实测眉毛部件的权重和落在 ForeArm 上），目前用「逐顶点最大权重投票（排除
表情骨）+ 离质心距离加权」的启发式，14 个部件里 10 个明确正确，
眉毛/部分脸部部件仍可能挂到手臂骨上。静止姿态不受影响（顶点是按所挂骨骼
的逆变换存的），但动作播放时这些部件会跟错。计划用**动作真值**（逐帧顶点）
反推归属，而不是继续猜。

## E16 批量抽检发现的源数据问题（已知，待 P4 解决）

抽检 `2DModel_ST_Tiamat_NS1`（47 部件）时，预览里出现了几块**位置错误、
漂浮在身体外的碎片**。逐项核对：

- 这些部件的 `max_err = 1.0e-06`，也就是 **模型顶点与我们的提取结果完全一致**；
- 所以问题不在 moc3，也不在 Live2D 侧，而是**提取阶段的 LBS 位置本身就错**：
  这些 SMR 的 `m_Bones` 顺序与网格 bindpose 顺序不一致（之前记录的
  “共享骨骼表”问题），导致部分顶点被错误的骨骼矩阵变换到别处。

**后续复核（2026-11-06 晚）：这个判断是错的，已推翻。**

用 `tools\compare_spine_bbox.py` 把同一部件与 **Spine 产物**（那条线已经和
Unity 运行时对过账）的世界包围盒对比：

```text
Spine: parts_Back_Hair_001_s0  x=[-68.14, 33.41] y=[-135.13, 76.71]   （像素）
我们 : parts_Back_Hair_001_s0  x=[ -0.91,  0.11] y=[  -1.81,  0.31]   （单位）
```

两边**尺寸完全一致**（dx≈1.01、dy≈2.12），只差一个整体平移（Spine 产物
自带坐标归一化）。也就是说：我们的 LBS 提取与已验证的 Spine 线一致，
那些「碎片」是**长后发发束本身**的形状，不是错位的顶点。

结论修正：

1. 批量的「一致性 + 顶点误差」证明打包正确，这一点仍然成立；
2. 「`m_Bones` 顺序错位」在这批资产上没有证据；之前的怀疑来自对
   **长条发束**的误读，不能作为结论；
3. P4 的价值回到它本来的位置：**整部件刚性跟随单骨**的误差太大
   （E15），需要按顶点分块/拟合，而不是修提取。

## E17 逐顶点骨骼归属 + 三角形分块（P4 第一版）

`src\unity2live2d\convert\attribute.py` + `pipeline.segment_part()`：

1. 用动作帧真值（LBS）算出每个顶点在「每根候选骨」下的预测轨迹；
2. 每个顶点选**累计误差最小**的骨；
3. 三角形按多数顶点的骨归属分块；
4. 每个分块 = 一个 ArtMesh，挂到该骨的 RotationDeformer 下。

误差对比（4 帧，ppu=1000）：

| 角色 | 顶点数 | 整部件刚性 RMS | 逐顶点分块 RMS | 降低 |
| --- | --- | --- | --- | --- |
| Alexandra | 450 | 668.3 px | **51.8 px** | 92% |
| Tiamat | 4,453 | 29.0 px | **1.3 px** | 95% |

产物规模（分块后）：Alexandra 14 部件 → 95 段（moc3 70 KB）；
Tiamat 47 部件 → 263 段；两者一致性均为 1、顶点误差 1e-6。

### 复核结论：Sprite 部件的参照本身偏移了 1 个单位

逐部件对比（`tools\compare_part_bbox.py`）：

```text
相机 sprite: Spine y=[-173.5,-104.1]   我们 y=[-74.3,-4.9]    差 +100（=1 单位）
旗子 sprite: Spine y=[ -58.4,  20.2]   我们 y=[ 40.8,119.4]    差 +100
```

- 我们：用 **Unity 自带 sprite render mesh**（`mesh_source='asset'`）+ 渲染器世界矩阵，
  这是 Unity 的绘制语义；
- Spine 产物：同尺寸、整体平移 +1 单位——是导出器的处理差异（不是我们丢件）。

因此 **sprite 占比越高的角色，和 Spine 的 IoU 天然越低**，实测：

| sprite 部件占比 | 数量 | IoU 中位数 |
| --- | --- | --- |
| < 0.2 | 93 | **0.953** |
| 0.2–0.5 | 19 | 0.783 |
| 0.5–0.8 | 35 | 0.751 |
| ≥ 0.8 | 10 | 0.500 |

结论：**IoU 只能用于「sprite 占比低」的角色**做判据；sprite 主导的角色需要
Unity 真值截图仲裁（本机没有 Unity 6，暂时无法生成）。

同时，Spine 产物完整性也很差：`Azaz_NS1`、`Alice_NS2` 的产物只有眼睛/雨伞
等零星部件，IoU 0.05 并不说明我们的输出有问题。

## E37 真正的根因：UV 的 V 方向「每个角色不一样」

对同一批模型做「构建时是否翻 V × 预览时是否翻 V」的四象限实验：

| 角色 | 构建翻V+采样翻V | 构建翻V+不翻 | 不翻+翻 | 不翻+不翻 |
| --- | --- | --- | --- | --- |
| Alexandra  | **0.968** | 0.191 | — | — |
| Brownie    | **0.962** | 0.254 | — | — |
| Khan       | **0.898** | 0.228 | 0.273 | 0.776 |
| RheinRitter| 0.554 | 0.897 | **0.912** | 0.472 |

（「构建翻V+采样翻V」与「不翻+不翻」是同一个朝向，「构建翻V+不翻」与「不翻+翻」也是。）

结论：**不同角色的源 UV 朝向不同**——Alexandra/Brownie/Khan 的 Sprite UV 需要翻，
RheinRitter 的不能翻；而对蒙皮网格再翻一次又会把 Brownie 弄坏（0.17）。
单一全局约定不可能正确。

### 正确做法（下一轮落地）

按角色**自动择优**：
1. 每个角色构建两个变体（翻 V / 不翻 V）；
2. 各渲染一次，与 Unity 自然真值算 IoU；
3. 取 IoU 高的那个作为最终包。

成本约 2 次构建 + 2 次渲染/角色（全量约 10–15 分钟），能同时消掉中位数与
RheinRitter 的差距（预期 RheinRitter ≈0.91）。

## E44 试过「把叠加发光烘焙进贴图」——对多数角色反而更差

思路（按要求）：moc3 v1 没有混合模式，那就把叠加/正片叠底的发光件烘焙成普通
alpha 贴图（`alpha_new = clamp(max(rgb)/255)`，RGB 直通），再按普通混合绘制。
实现见 `src/unity2live2d/convert/texture_bake.py`（只改该部件在图集里的矩形，
矩形互不重叠，所以不会影响别的部件）。

| --- | --- | --- |
| WarWolf_NS1 | **0.976** | 0.171 |
| Scathy_N | **0.976** | 0.348 |
| Aeda_N | 0.749 | 0.746 |

结论：烟雾/横幅这类特效在 Unity 的「自然状态」截图里本来就几乎不可见，
烘成不透明只会变成更大的错块；Aeda 则完全没有改善。**已回退为「跳过」**。

### Aeda_N 为什么只能到 0.749

对比图（`Products\_aeda_bake.png`）：我们的是**清晰的角色 + 圆环**，
Unity 自然截图是**整片泛光/发虚**的版本（大量加色 glow 叠加）。

- precision 0.955（我们画出来的几乎都对），recall 0.776（少了 22% 的泛光面积）；
- 这 22% 就是 Unity 里那层泛光，moc3 v1 无法表达；硬要匹配只能把泛光烘成
  大块半透明遮罩，那会让成品明显变脏，得不偿失。

当前全量：`>=0.85` 的角色 **156/157**，唯一例外就是 Aeda_N（0.749），
它属于「参考图本身带泛光」的评估偏差，而不是转换错误。

## E45 Aeda 的差距是「整圈泛光/描边」，不是某个部件

叠加图（`tools\mask_overlay.py`）显示：蓝色（Unity 有、我们没有）是**沿整个剪影
的一圈均匀外扩**，不是某几个特效件。

数据：precision 0.955、recall 0.776；我们的面积 113k，Unity 139k（+23%），
而包围盒几乎一致 —— 这是「轮廓被均匀加宽」，典型是泛光/描边。

| --- | --- | --- | --- |

### 结论

## E48 读 `Assets\Raw\Scripts`：控制件的显隐是 Puppet2D 脚本用「精灵名」判的

脚本目录里与本问题相关的是 Puppet2D 那一套（AssetRipper 反编译）：

| 脚本 | 作用 |
| --- | --- |
| `Puppet2D_GlobalControl.cs` | 全局控制件显隐：`UpdateVisibility()` 按序列化开关设置 |
| `Puppet2D_HiddenBone.cs` | 只做朝向/缩放，不切显隐（34 个 `hiddenBone_*` 上挂的就是它） |
| `ActorPartsView.cs` / `Actor.cs` | 只剩序列化字段（反编译失败，是 Dummy），没有逻辑 |

关键在 `Puppet2D_GlobalControl`：

```csharp
foreach (SpriteRenderer r in this._Controls)
    r.enabled = this.ControlsVisiblity;        // 默认 0
foreach (SpriteRenderer r in this._FFDControls)
    r.transform.parent.gameObject.SetActive(this.FFD_Visiblity);  // 默认 0
```

而 `_Controls` / `_FFDControls` 是在 `TraverseHierarchy()` 里按**精灵名**收集的：

```csharp
if (component.sprite.name.Contains("Control")) this._Controls.Add(component);
else if (component.sprite.name.Contains("ffd")) this._FFDControls.Add(component);
```

prefab 里这些开关是序列化字段，可以直接读：

```text
2DModel_3P_Alice_NS1_DL_N.uAnim.prefab:
  ControlsVisiblity = 0   BonesVisiblity = 0   FFD_Visiblity = 0   ControlsEnabled = 1
```

**结论**：控制类部件（IK 圆环、控制柄等）的隐藏规则是
「精灵名含 `Control`/`ffd` 且 `ControlsVisiblity`/`FFD_Visiblity` 为 0」，
完全可以从 prefab + sprite 名静态判定 —— 这比现在的「控制组 + 命名」启发式更准确。

### 仍无法解释的部分
