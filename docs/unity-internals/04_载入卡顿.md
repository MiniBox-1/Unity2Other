# tq.txt 第 4 条：载入十分卡顿

> 要求：提高加载速度，如将 json 转化为 Binary，测试是否将多骨骼而不是单骨骼可以提高加载速度。

## 4.1 结论（先给答案）

| 问题 | 答案 | 实测 |
| --- | --- | --- |
| **JSON → Binary 有没有用？** | **非常有用**：产物目录里放 `.skel` 后，查看器**优先读二进制**（`detect_spine_dir` 的 `_skel_rank` 把 binary 排在最前） | 同一角色同一帧：`.json` **112.7 s** → `.skel` **15.9 s**，**快 7.1 倍** |
| **多骨骼能不能更快？** | **理论上是**（形变数据会大幅变小），但目前产品是"**只有 Root 一根骨 + 每个顶点逐帧 deform**"，改成真骨骼蒙皮是一次**架构级改动**，见 4.3 | — |
| 另一半瓶颈 | **内存**：渲染/加载一次峰值 **13 GB**（本机 15.8 GB 物理内存），一旦和别的重活并行就整机卡死 | 见 4.4 |

## 4.2 `.skel`（二进制）—— 已经可以做，且已写好工具

```powershell
# 给整个产物根目录里所有角色写 .skel（JSON 变过时必须 --force）
python tools\write_all_skel.py _probe50_rt3 --force
```

写出器是**原生实现**（`ngui2spine/spine38_binary_writer.py`），并且与第三方
`SpineSkeletonDataConverter.exe` 的输出**逐字节一致**（回归命令：
`python tools\check_skel.py _probe50_rt3\banshee_skin1 --ref-exe`），
所以把 `.skel` 当交付件是安全的（查看器、Spine 运行时都能直接吃）。

**为什么 JSON 这么大**（这就是卡顿的第一原因）：我们的骨架只有 `Root` 一根，
所有部件都是 mesh，动画把**每个顶点的逐帧位移**写进 `deform`：

| 角色 | `*_static.json` |
| --- | --- |
| draculina_skin1 | **245 MB** |
| cheona_skin1 | 203 MB |
| cerberus_skin3 | 150 MB |
| alice_skin1_fix | 110 MB |
| alice_skin1_dl_idle | 108 MB |

## 4.3 多骨骼方案（tq.txt 里问的那条）

现在的形态：`Root` 一根骨 → 所有部件的形变都靠 deform 逐帧写。
改成"多骨骼 + 蒙皮权重"后：

* 顶点位置由骨骼矩阵算出来 ⇒ **deform 可以只写真正需要的（blendShape / 布料）**，
  JSON 通常能小一个数量级，加载也会跟着快；
* 但需要：导出真实骨骼树（或者用现在解析到的 Unity 骨骼树）、每个顶点的
  **boneWeights**（我们已经在 `SceneT0`/`PoseFrames` 的对比里用过，
  解析侧是现成的）、以及把"Unity 的层级变换"映射成 Spine 的骨骼顺序；
* 风险：Spine 3.8 的蒙皮顶点上限（每顶点 4 骨）与我们部件的实际权重需要核对；
  drawOrder/相对层级那条线（3.24）也要跟着重新验一遍。

**建议步骤**：先在**一个**中等角色（例如 `banshee_skin1`，1 页图集、JSON 也不小）
上做原型，用 `calib_geo`（对 PoseFrames 逐顶点）+ `check_clip_visibility` 验收，
再决定要不要全量切。

## 4.4 内存（另一半"卡"）

实测（`PeakWorkingSet64`，子进程一起数；本机物理内存 **15.8 GB**）：

| 动作 | 峰值 |
| --- | --- |
| **`rt_frames.py` 渲染 1 帧**（alice_skin1_fix 900 / draculina 900 与 2000 峰值相同） | **13.0–13.2 GB** |
| `rt_frames.py`（`constantias2_skin0`，JSON 只 8 MB） | 2.35 GB |
| Unity `ModelInspect.All`（1 角色 2 帧） | 1.84 GB |
| `check_play_visibility.py`（1 角色） | 1.12 GB |
| 单角色转换 | 0.68 GB |
| `convert_all_2dmodel.py --jobs 4` | 子进程峰值和 **3.67 GB**（父进程只有 39 MB） |

⇒ **一次只跑一件重活**；`convert_all_2dmodel.py --jobs` 给 2；
渲染不要与 Unity 批处理/校验循环并行；重活并行前先用 `tools\mem_probe.ps1`
量进程树峰值内存。详见 `docs/交接必看.md` 铁律 2。
