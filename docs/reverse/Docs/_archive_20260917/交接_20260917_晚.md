## 1. 修了什么：同 `sortingOrder` 内的次序 = **层级 DFS 序**

**现象**：`cerberus_skin1` 表情重叠 —— Unity 里星形瞳孔压在普通眼之上，
我们这边普通眼皮把星形瞳孔盖住（用户给的两张图就是这个对比）。

**根因**：Unity 透明件的排序键是 `(sortingLayer, m_SortingOrder, 到相机深度)`。
2D 角色所有部件 z 基本相同（实测 `_refshot_cerberus_skin3` 103 个渲染器里
**101 个 camDepth = 10.000、2 个 10.002**，后者来自网格自身的 z 厚度），
所以同 `m_SortingOrder` 内的先后**完全由"渲染器列表序"决定**；而我们的
`order_at()` 用的是 **prefab/场景文件里的出现顺序**，与它无关。

**证据（三条，互相独立）**

1. `_refshot_*`（新格式 Unity 参考帧）逐渲染器带 `sortingOrder` / `camDepth`
   ⇒ 同 `sortingOrder` 内深度并列，必须有别的次序规则。
2. `info/Data/PlayFrames/*.json` 的 `renderers` 数组（`GetComponentsInChildren
   <Renderer>(true)` 的产物）在 **SpriteRenderer 段内与 prefab 层级 DFS 序
   逐项相同**：`cerberus_skin1` 是 `eye_1 → eye_star1 → eye_star2 →
   eye_star1_R → eye_star1_L → eye_OO → eye_sleep → mouth_1 → mouth_big …`。
   ⚠️ 这个数组是 **"SMR 段 + Sprite 段"两段拼接**（旧 dumper 分两趟写），
   所以只有**同一段内**的相对顺序有意义，别拿它对全表。
3. Unity 截图里星形瞳孔在普通眼**之上**；文件序恰好相反（`eye_1` 在
   `eye_star1` 之后）。⇒ 文件序必错，DFS 序与截图一致。

**改法**（`ngui2spine/static_prefab_spine.py`）

```python
hierarchy_ranks(mdl)        # 层级 DFS 序（tops → 按 m_Children 深度优先）
slot_key_with_rank(rank)    # key = (sortingOrder 取整, 同值内 DFS 序)
kept.sort(key=slot_key_with_rank(hierarchy_ranks(mdl)))   # 原来是 _slot_key（只看 sortingOrder）
```

`tools/layer_report.py`（相对层级诊断）同步用同一个键；`order_at()` 的注释也改了。

**回归（按要求只跑 audrey）**

| 与上一版逐项对比 | `skins` **完全相同**；`animations` **逐字节相同**；槽位元数据（bone/attachment/color/blend）作为字典相同 ⇒ **只有槽位顺序变了** |

## 2. 修了什么：`beasthunter_skin1 动不了` = **atlas 少一个尾换行，spine-cpp 越界读**

**现象**：`rt_frames.py` 渲任意动画、任意尺寸都 `0xC0000005`；把 `.skel` 删掉
只留 JSON 也一样。**关键**：`_scratch/q2_spine_load.py`（不建 GL，只构造
`SpineData`）也能复现 ⇒ **加载期**的数据问题。

**定位**（`_scratch/q3_spine_bisect.py`，每轮子进程加载）

| 组合 | 结果 |
| --- | --- |
| banshee 骨架 + banshee atlas | OK |
| **banshee 骨架 + beasthunter atlas** | **CRASH** |
| beasthunter 骨架 + beasthunter atlas | CRASH |
| beasthunter 骨架 + banshee atlas | CRASH |
| banshee 骨架 + beasthunter 骨架的 `bones` | OK |
| （其余单块互换） | 因 region/附件对不上而崩，**不可用**作判据 |

⇒ **atlas 是元凶**。再把 atlas 本身做矩阵（`_scratch/q3_atlas_probe.py`）：

| atlas | 大小 | 结果 |
| --- | --- | --- |
| beasthunter 原样（2 页，无尾换行） | 416 B | **CRASH** |
| 末尾 +`\n` | 417 B | OK |
| 末尾 +空格 / +`\r\n` / +`#x\n` / +`\0` | 417~419 B | OK |
| 砍掉最后 1 字节 | 415 B | OK |

⇒ **文件正好在最后一行属性处结束（EOF 无换行）时，spine-cpp 3.8 的 `.atlas`
解析会越界读**；补/减任意 1 个字节就躲开。**只有多页 atlas 触发**，单页不触发
（所以以前一直没发现）。

50 个产物里多页 atlas 的只有 **2 个**：`beasthunter_skin1` 与
`blacklilith_skin2`（都是 2 页、都 416 B）—— 两个都崩。

**改法**（`ngui2spine/spine_out.py::atlas_text`）：结尾 `return "\n".join(out) + "\n"`。

**验证**

| 角色 | 重导后 `static_check` | `q2_spine_load` | `rt_frames` |
| --- | --- | --- | --- |
| `beasthunter_skin1` | 四项 0（34 渲染器 / 32 部件） | **OK**（lobby/Tep_1/breast） | OK，出图正常（坐在火箭上的姿态） |
| `blacklilith_skin2` | 四项 0（53 / 52） | **OK**（5 条动画） | OK |

## 6. 新增：Unity 侧"渲染顺序"导出（回答"谁盖谁"的实证工具）

第 1 节的结论是**从真值推**出来的；要把它变成**实测**（不靠推断），用这对新工具：

| 文件 | 干什么 |
| --- | --- |
| `Assets\Editor\ExportDrawOrder.cs`（Unity 工程里） | Play 模式下导出每个渲染器的排序信息（路径/类型/枚举序/DFS 序/sortingLayer/order/深度/包围盒/屏幕框/sprite/材质/混合/显隐）**以及成对隔离渲染实测出来的先后**；参数硬编码在 `ExportDrawOrderPlan` |
| `tools\read_draworder.py`（本项目） | 读上面那份 JSON，直接回答：枚举序是否等于 DFS 序、每个并列组实测顺序与 DFS 是否一致、全局顺序用"DFS 当并列次序"解释后还有多少逆序对 |

怎么跑（**菜单，不是 batchmode**）：

1. 需要哪几帧就改 `ExportDrawOrderPlan`：`Names` / `States` / `Times`（**秒**）/
   `PairScope`。`PairScope="tie"` 只测"排序键完全并列"的组（快，直接回答同 order 谁盖谁）；
   `"all"` 会测所有互相重叠的可见渲染器，给出**完整经验绘制顺序**（n² 量级，一个角色
   约几百~两千张隔离图，几十秒）。
2. 目标怎么来（这块是 2026-09-17 晚补的）：
   · `Names="a,b,c"`：按名字找；**场景里没有的名字**（例如 `cerberus_skin1` —— 你的
     场景里只有 `cerberus_skin3`）只要 `InstantiateMissing=true`，就从
     `PrefabDir`（默认 `Assets/prefabs/Change50`，就是转换用的那 50 个 prefab）**临时
     实例化一份**来采，采完 `DestroyImmediate` 销毁。
   · `Names=""` 或 `"*"`：**场景里全部**带 Animator+Renderer 的根。
   · **场景里的角色一律是 inactive**（`2.unity` 里 7 个角色的根 `m_IsActive` 全是 0），
     脚本会把整条父链**临时激活**再采、采完恢复 —— 不激活的话 Animator 不跑、
     渲染器不提交，采到的顺序是假的。日志里会写"其中 inactive N 个"。
3. 菜单 `Tools/2DModel/运行时采样/渲染顺序导出：按内置清单开始`（会自动进 Play，采完退出；
   日志 `D:\VB\Unity2Spine\info\_logs\play_sample.log`）。
4. 产物 `info\_draworder_<角色>\...json` + `frames\*.png`（白底 + `_cam.txt`，可给 `cmp_truth.py` 用）。
5. `D:\Anconda\python.exe tools\read_draworder.py "info\_draworder_<角色>" --verbose`
   —— 如果打印 `⇒ DFS 序可以完全解释这份实测顺序`，第 1 节的规则就算被实测盖章；
   如果某些并列组标 `✗`，把那些组的实测顺序贴回来，规则要按实测改。

判定"谁在谁上面"的原理（脚本注释里也写了）：对每对 (a,b) 单独渲染三张图
（只开 a / 只开 b / 两个都开），用"不透明像素投票"+"两种混合模型的误差"两条证据
判定；两条一致才下结论，否则在 `pairs[].verdict` 里标 `?votes` / `?model` / `ambiguous`。

### 9.1 第一次跑（16:41，60 目标 / 842 帧）**全是空帧** —— 已排查并修

**现象**：日志里每帧都是 `渲染器 101，含并列的组 0，实测对 0`；JSON 里
`enabled=true` 的渲染器 **0 个**、`isVisible=true` **0 个**；`frames\*.png` 是白底空图。
842 帧全部作废（已按"只挪不删"挪到 `lastOrign\_bad_draworder_20260917_1641\`，只留下
15:46 那两份好数据：`_draworder_cerberus_skin1` / `_draworder_banshee_skin1`）。

**根因**：`Names="*"` 当时把"场景里**任意**带 Animator+Renderer 的 GameObject"都当目标，
于是**角色内部的子物体**（`size_root` / `Size_root` / `ch_root` / `bone_R_wing` /
`bone_L_wing` / `GameObject` …）也进了目标名单（60 个名字里约 10+ 个是子物体，
同名重复还互相覆盖目录）。后果是：导出真角色 `PECS_Draculina_NS1` 时，脚本把"其它目标"
——包括它**自己的子节点 `size_root`**——整根 `SetActive(false)`，整棵子树当场灭掉，
于是这一帧没有任何渲染器是 enabled/visible，成对实测自然 0 对。

**修法**（`ExportDrawOrder.cs`）：

1. `"*"`/空名单只取**候选集合的根**：丢掉"祖先也在候选里"的对象（日志会打印
   `候选 N 个里有 K 个是角色内部子物体，不作为独立目标：…`）。
2. 关"其它目标"时跳过**与目标有父子关系**的对象（两个方向都查），免得把目标自己的
   子/父节点关掉；关"名单外的场景根"时也排除目标的祖先。
3. 加安全网：一帧里"真的会画"的渲染器为 0 就直接
   `[draworder] ...：可见渲染器 **0** 个 ... 这帧是空的，检查目标选择`，
   正常帧的日志也带上 `可见 N`（`渲染器 101，可见 89，含并列的组 …`）。

**下次跑的顺序（建议）**：先 `States="lobby"` + `Times="0.5"` + `PairScope="tie"` 小跑一遍
（约 50 帧、< 1 分钟），确认日志里每帧 `可见 N` 都 > 0、没有再报"0 个"；再换成
`States=""`（全状态）+ 5 个比例时刻 + `PairScope="all"` 跑全量。

### 9.2 第二次跑（16:51，56 目标 / 1275 帧）**还是空帧** —— 真正的原因是 **Renderer 级 disabled**

修了"嵌套子物体"之后重跑，日志仍然是

### 9.3 用户反馈："这样渲染出来和直接 PlayMode 打开不一致" —— 改成 **observe 模式**

一句到位：**我们是在"制造"一个游戏永远不会出现的状态**（脚本自己 `SetActive` +
强开 `Renderer.enabled` + 把别的角色关掉），采到的画面当然不是玩家在 Play 里看到的。

改成两种模式（`TouchMode`）：

| 模式 | 行为 | 用在哪 |
| --- | --- | --- |
| **`observe`（新默认）** | **一个字节都不改场景**：每帧扫一遍还没采的目标，**谁被游戏正常显示出来**（根 `activeInHierarchy` 且有 `enabled` 的渲染器）就采谁，顺序由游戏决定；到 `ObserveTotalSeconds`（默认 900 s）或全采完就收工。没出现的目标在日志里逐个记账。 | 想要"和直接 Play 一致的画面"时 |
| `force`（旧做法） | 脚本自己激活 + 强开渲染器 + 关掉别的角色，逐个采 50 个 | 游戏自己显示不出来时才用 |

配套：

- `IsolateFrame`（默认 **false**）：主帧 PNG **就是正常 Play 的画面**（可能同时有别的角色）。
  成对隔离渲染**永远**会把别的角色临时关掉，但只影响"谁盖谁"的判定，**不影响主帧**，
  而且渲完立刻还原。
- `OnlyInactive` 在 observe 模式下**自动忽略**（那时我们要的正是"游戏显示出来的那一刻"）。
- observe 模式下如果某个 Animator 原本是 disabled，会临时打开（否则没法按状态采样），
  采完**还原**。
- observe 模式下安全网照旧：一帧的"可见渲染器"为 0 会报 ERROR。
- **退出 Play 自动停**（2026-09-17 晚加）：`playModeStateChanged` 里 `ExitingPlayMode` /
  `EnteredEditMode` 一到就 `StopRunning()`，`Pump` 每次也先查 `EditorApplication.isPlaying`；
  另外两个循环和 `SampleTarget` 的每个 yield 点都会检查。停止时 `Dispose()` 协程 ——
  迭代器里各目标的 `finally`（关回 inactive / 还原渲染器）会立刻执行，`Run` 的 finally
  再兜一次底（还原 `_activated`、销毁临时实例化对象），日志写
  `[draworder] 已停止（原因）` + `收尾完成`。**不会再出现"退出 Play 后脚本还在 edit
  模式里继续采、继续改场景"**。

**怎么跑**：进 Play，用你平时的方式把角色显示出来（游戏自己的流程 / UI / 你自己的
`SceneActivationController` 都行），脚本会自动把出现的每个角色采下来 ——
**显示多少采多少**，不需要我们替它打开。
