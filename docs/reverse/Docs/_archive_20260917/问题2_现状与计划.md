## 四、今天查到哪了（2026-09-17 下午）

### 4.1 `beasthunter_skin1` "动不了" —— 已定位：**我们的产物让查看器崩溃**

用查看器的渲染器（`tools/rt_frames.py`，走的是 `render_lib` → spine-cpp）渲染
`beasthunter_skin1` 的**任意一条动画**（lobby / Tep_1 / breast）都会
**访问冲突退出**：

```text
Windows fatal exception: access violation
  File "renderer_src\Spine\SpineOperator.py", line 130 in __init__
  File "renderer_src\SpineRender.py", line 628 in Update
exit=-1073741819 (0xC0000005)
```

- 换成 **JSON**（把 `.skel` 拿掉）也一样崩 ⇒ **不是 `.skel` 写错，是数据本身**让
  spine-cpp 解析时炸掉。
- 对照：同一套流程渲染 `banshee_skin1`（4 条动画）**全部正常**
  ⇒ 崩溃与角色数据有关，不是环境问题。
- 结构体检（`_scratch/q2_json_audit.py`：NaN/Inf、重名、槽↔附件引用、
  mesh 的 vertices/uvs/triangles、动画引用的槽/附件、deform 帧长）**没有报错**；
  JSON 里也**没有重复键**。
- 下一步：继续二分（把 beasthunter 的 `bones/slots/skins/animations` 逐块换进
  banshee 的能跑文件里），定位到具体哪一块。产物规模不大（JSON 4.5 MB），
  所以这不是内存问题。

### 4.2 `cerberus_skin1` "表情重叠" —— 已定位到**绘制顺序**

- 先用 Play 真值逐帧比显隐：**4 个状态、396 帧全部一致**（`check_play_visibility`
  0 处不一致）⇒ 不是"多显示了几个件"。
- 用户给的 Unity 截图里，眼睛是**星形/心形瞳孔压在普通眼睛上面**；
  我们的渲染里是**普通眼皮那块压在星形瞳孔上面**。
- 查数据：`parts_eye_1 / eye_star1 / eye_OO / eye_sleep` 的 `sortingOrder`
  都是 **17**（同 order），所以谁盖谁由**同 order 内的绘制顺序**决定：
  - Unity（真值枚举序，按层级 DFS）：`eye_1 → eye_star1 → star2 → star1_R →
    star1_L → eye_OO → eye_sleep → mouth_1 → mouth_big …`
  - 我们（`parts` 按 **prefab 文件出现顺序**）：`mouth_big → mouth_1 → eye_OO →
    eye_star1 → eye_1 → mouth_neco2 → mouth_mini → eye_sleep`
  ⇒ 我们把 `eye_1` 排在 `eye_star1` **之后**画，于是普通眼压住了星形瞳孔。
- **待修**：把 `order_at()` 的"同排序值内的静态次序"从"prefab 文件顺序"改成
  **层级 DFS 顺序**（Unity 的渲染器枚举顺序 = 深度优先、children 按
  `m_Children` 顺序）。改完要按规矩**只挑一个主力角色**回归。

### 4.3 `banshee_skin1` lobby 手 —— 目前是"真值本身可疑"，不是我们的显隐问题

- 显隐：`check_play_visibility` 对 banshee 的 lobby **0 处不一致**（4 条动画里只有
  Tep_1 有 1 个 slot 差 1 帧）。
- 手/手指的 `m_IsActive`、`m_SortingOrder` 我们与 Unity 完全一致
  （`parts_Hand_R*` 44~48、`parts_Finger_R3/4/5` 46~48、`parts_Hand_L*` 负值那一组）。
- 用同帧对照（`_scratch/cmp_truth.py` + `_inspect_banshee_skin1/frames/breast_t0.png`）：
  - **breast t=2.0：我们和 Unity 基本重合**（差异只在边缘抗锯齿）；
  - **breast t=0：手/头发那片区域差得很大** —— 但同一时刻的 **PoseFrames 真值本身是坏的**
    （`parts_Hand_R` 的头三个顶点是 `-1010 / -3637` 这种量级，BakeMesh 在 t=0
    还没把 pose 应用上去），所以 **t=0 这一帧不能当判据**。
- 结论：先按 4.2 的绘制顺序问题一起修（同样的"同 order 内顺序"机理），
  修完再渲染 lobby/breast 同帧复核；如果还对不上，再请你在 Unity 里采
  "banshee lobby 同帧 + 逐渲染器"的参考帧（`PlayRefShot`，见
  `tq_report/05_待你导出的参考帧.md`）。
