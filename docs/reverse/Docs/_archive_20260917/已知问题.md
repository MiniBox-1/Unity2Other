## 1.5 ~~**`alice_skin2` 伞的位置错：精灵挂在 pivot 的另一侧**~~ ✅ **已修（2026-09-15 晚）**

> **结论**：`m_FlipX / m_FlipY` 旧实现是"只换 UV、几何不动"，而 Unity 是
> **绕 pivot 镜像几何**。pivot 居中时两者等价，pivot 不居中 + 精灵细长时
> 就差一整个精灵长。修法见 `静态prefab路线.md` **3.25**（两处：建四边形 +
> `_part_points`；`_part_uvs` 里的翻转要删掉，否则翻两次）。
> **验证**：`alice_skin2` lobby t=0 伞的中心/尺寸与 Unity 运行时**逐位相同**
> `(0.7033, -0.9507)` / `(0.2456, 1.8728)`；离线渲染手握着伞柄；
> 影响面 82/1940 个 prefab；三主力静态检查四项全 0。
> 下面保留定位过程备查。

用户在 `Question/alice_skin2拿的伞位置不对.png` 报"手里伞反了或位置不对，应该拿的是
伞柄"。我们的产物里伞整体比 Unity 运行时高 **1.752 世界单位（1144 源图像素）**。

### 具体落点（2026-09-15 晚，已查到资源）

sprite 本体：`Assets\rawLo\alice\alice_skin2\Sprite\parts_Umbrella_Sprite_s32.asset`

m_Offset: {x: -574.5065, y: 2.0000014}
m_Pivot:  {x: 0.03177463, y: 0.5131579}

`m_PixelsToUnits`，`m_Offset` 读了但 `convert_2dmodel.py` 构造四边形时完全没用**：

l = -rect[2] * px / units      # 只用 rect 与 pivot

中心 pivot、`m_Offset ≈ 0` 的精灵（嘴、贴片）这条 bug 完全看不出来 —— 这就是
"只有伞偏、其它部件逐顶点全对"的原因。

**影响面已扫**（`Assets/rawLo/*/*/Sprite/*.asset`，7921 个 sprite）：

## 1.6 ~~**精灵按"矩形"整块导出，把邻近图素的像素一起画出来了**~~ ✅ **已修（2026-09-16）**

> **结论**：改成 Unity 的 **Tight 网格** —— 新增 `ngui2spine/sprite_outline.py`
> （掩码 → 膨胀 → 轮廓 → 丢小岛 → 归一化容差简化 → 三角化），
> sprite 分支优先用它、失败回落四边形；`_part_points()/_part_uvs()` 改为直接用
> 部件自己的网格。**逆向依据**（`UnityPlayer.dll` + PDB）：`GenerateSpriteOutline`
> → `SpriteMeshGenerator::MakeShape` → `mask/contour/select/simplify`，
> 容差是归一化的 `[0,1]`、并且有"顶点预算驱动的迭代放松"。
> **验收**：`parts_Horn_L` 变成 **9 顶点 / 7 三角形**（Unity 同样 9/7），
> `alice_skin1_dl_idle` lobby t=0 的 24 px 小黑点**消失**；三主力四项全 0；
> 16 个点名角色 `check_clip_visibility` 15/16（与改前一致）；JSON +2%。
> 完整数字见 `静态prefab路线.md` **3.26**。下面保留定位过程备查。
>
> **2026-09-16 下午补充（见 1.7）**：这次复刻对**大 sprite 明显不够紧** ——
> `banshee_skin1` 的 `parts_Head`，我们的多边形盖住矩形面积的 **73%**，
> Unity 只盖 **37%** ⇒ 多盖且不透明的像素 **39 454 个**，这正是用户报的
> "头上 / 脸上碎块"。同时发现**精灵资产里就存着 Unity 自己生成的网格**
> （`m_RD.m_VertexData` + `m_IndexBuffer`，与运行时逐位一致）⇒ 下一步不再
> 复刻算法，改成直接读资产网格。

（编号接在 1.5 后，便于和"伞"那条一起看；2026-09-15 晚定性，**待修**）

### 现象

用户截图 `alice_skin1_dl_idle小黑点.png`：`lobby` 里角色**右上角（两只角之间）飘着
一个小黑三角**。我们的离线渲染复现了；**Unity 自己渲染同一帧没有**
（`ModelInspect` 出的 `_inspect_alice_skin1_dl_idle\frames\lobby_t0.png`，
同一世界坐标处是空白）。

### 定位过程

1. 渲染图连通块分析：黑点在 1000² 图上的 `x[613,620] y[168,173]`（24 px）；
2. 用产物 setup AABB `x[-921.6,921.6] y[-697.7,697.7]` 反解 → 源图像素
   `(214.7, 607.4)` → 世界 `(0.2877, 0.7429)`；
3. 遍历所有槽位：**只有 `parts_Horn_L_122` 覆盖该点**；
4. 但和 Unity 运行时比**这个部件的 AABB 是对的**：

   | | boundsCenter | boundsSize |
   | --- | --- | --- |
   | Unity 运行时（`ModelInspect`） | `(0.0698, 0.622)` | `(0.4569, 0.501)` |
   | 我们产物 | `(0.0730, 0.6221)` | `(0.4555, 0.4998)` |

5. 于是去看**贴图**：`parts_Horn_L` 用的 sprite 是
   `rawLo\alice\alice_skin1_dl_origin\Sprite\FullBodyIMG_3P_Alice_NS1_part1_15.asset`
   （`m_Rect {194, 1660, 319, 350}`、`m_Pivot {0.5, 0.5057}`），把产物图集里对应
   区域裁出来一看 —— **矩形的右上角有一块"邻居犄角尖"的黑三角**（见
   `_scratch\horn_tex.png`）。这一块在 `m_Rect` 里、而且是不透明的。

### 根因

Unity 的 sprite 会按 **Sprite Mesh Type** 生成渲染网格：**Tight** 时网格贴着
alpha 轮廓走，`m_Rect` 里混进来的邻居图素**不会被画**；**FullRect** 时才是一整块四边形。
我们的转换器**永远发一整块四边形**（`convert_2dmodel.py` 里按 `m_Rect` 拼四角），
所以只要某个 sprite 的 `m_Rect` 里混进了别的图素（手绘 sheet 上很常见），
我们就会把它一起画出来。

**决定性证据（2026-09-15 晚，从 Unity 侧直接问精灵自己的网格）**：
给 `ModelInspect` 加了 `Sprite.vertices` / `Sprite.triangles` 的导出
（`renderers.json` 里的 `spriteMeshVerts` / `spriteMeshTris`），跑
`alice_skin1_dl_idle` 的结果：

| 精灵 | Unity 生成的网格 | 我们发的 |
| --- | --- | --- |
| `parts_Horn_L` | **9 顶点 / 7 三角形** | 4 顶点 / 2 三角形 |
| `parts_Horn_R` | 30 顶点 / 37 三角形 | 4 / 2 |
| `parts_Head` | 25 三角形 | 4 / 2 |
| `parts_Eye_1` | 14 三角形 | 4 / 2 |
| … | 该角色 **111 个 sprite 里 110 个都是 Tight**（只有 1 个是 2 三角形） | 全部按 2 三角形发 |

也就是说 **Unity 画的几乎全是紧致网格**，我们画的全是矩形 —— 差别不只"邻居图素"，
连**边缘贴合**都不一样（不过边缘只影响 1~2 px，肉眼多在缩放/抗锯齿上看不出来，
真正看得见的就是这种"矩形里混进别人图素"的漏画）。

> 顺带核实：那个小黑点所在的贴图像素（503, 1920，bottom-origin）**只被
> `part1_15` 这一个 sprite 的矩形覆盖**，没有别的 sprite 覆盖它 ——
> 所以它只能靠"按 alpha 生成 Tight 网格"排掉，靠"减掉别人的矩形"是排不掉的。

**又往前走了一步：Unity 的网格不是"贴着 alpha 的轮廓"，而是"简化过的多边形"**

把 `Sprite.vertices / uv / triangles` 全部倒出来算了一遍（`parts_Horn_L`）：

| 量 | 值 |
| --- | --- |
| Unity 网格 | **9 顶点 / 7 三角形（一个 9 边形）**，面积 **8.53**（单位²） |
| 该 sprite 矩形 | 3.19 × 3.50 = **11.17** |
| 矩形内 alpha（>8）实际面积 | **2.72**（最大连通块 2.70，另有 109px / 3px / … 的小岛） |
| 小黑点所在的 sprite 局部坐标 | `(-1.1136, -1.3255)` → **不在** Unity 网格内 |

也就是说：Unity 的 sprite 网格面积比 alpha 面积**大 3 倍多**，它是个**被简化过的
粗多边形**（把复杂轮廓拟合成 9 个点），那个 109px 的孤立小岛正好被**简化掉的角**
切在外面 —— 所以 Unity 不画它，我们画。

> ⇒ **"照 alpha 提紧致轮廓"并不能修好这条**（紧致轮廓会把那个不透明小岛包进去）。
> 要完全复刻，就得复刻 Unity 的 alpha→轮廓→简化 算法（不现实）。

**可行的修法**（按代价排序）：

1. **去小岛**（推荐，便宜且直接命中这条）：对每个 sprite 的矩形算 alpha 连通块，
   把**面积小于阈值**的孤立小岛判为杂点，从网格/贴图里去掉。对 `parts_Horn_L`
   就是去掉那 109px 的小岛（主块 27045px 不动）⇒ 小黑点消失。
   风险：艺术图上"本来就是独立小块"的（比如单独的高光/星星）会被误删 ——
   所以阈值要小、并且**只删"不被任何其它 sprite 矩形覆盖"的岛**（这种岛按定义
   就是杂点，不是别人的图素）。
2. **按 alpha 生成轮廓网格**：观感更接近 Unity（边缘贴合），但**修不了这条**
   （见上），而且会让顶点数暴涨、deform 数据变大。
3. **不改**：接受这类几 px 的漏画（当前状态）。

### 根因（与 1.6 / 3.26 同一条，但复刻得不够紧）

`sprite_outline.py` 复刻的是"掩码 → 膨胀 → 轮廓 → 丢小岛 → 归一化容差简化"，

  m_RD.textureRect / uvTransform / downscaleMultiplier -> 换算 uv

## 6. 同名孪生节点：同一父节点下**路径完全相同**的两个对象（2026-09-17 登记）

### 现象

`brownie_skin1` 的左手：Unity 里画着的那根手指，我们的产物里没有（该 slot 被整段隐藏）。

### 证据

1. prefab 里 `…/Bone_L_arm_hand/Bone_L_arm_finger2/` 下有**两个**都叫
   `parts_L_arm_finger` 的 GameObject：一个 `m_IsActive: 0`、一个 `m_IsActive: 1`，
   两者网格/位置相同；`_scratch/scene_flags.py` 解析场景得到同样结论。
2. clip（`BR_Brownie_NS1_2DModel_Lobby*.anim`）里只有一条常量 0 的
   `m_IsActive` 曲线，`path` 就是这条路径。
3. Play 参考帧 JSON 里这条 `path` 出现**两次**：一条 `activeSelf=False`、
   一条 `activeSelf=True` ⇒ **Unity 只把那条约曲线绑给其中一个对象**
   （另一个保持 prefab 值），而我们按"路径 → 曲线"查表会给两个都套上曲线。

### 影响

`parts_L_arm_finger(×2)` 在 20/20 帧上对不上（3.37 陷阱 4）。两个对象网格完全相同，
所以**画面上没有差别**；但如果哪天孪生件的网格不同（或一个被曲线换成别的
attachment），就会明显少画一块。当前按现状记录，不修。

### 建议修法

给节点引入"同名序号"维度：`hashed/curve 路径 + 第几个同名兄弟`，
按 Unity 的绑定规则（**同路径只绑第一个**）决定谁吃曲线、谁保持 prefab 值。
落点：`unity_2dmodel.py` 建 `transforms` 时给同路径节点编号，
`static_prefab_spine.py` 的 `_curve_lookup` / `part_visible` 带上序号。

### 复现

```powershell
python _scratch\truth_chain_probe.py _probe50_rt4 <工程根> brownie_skin1 --full
python _scratch\scene_vs_prefab.py _scratch\_scene2_flags.json brownie_skin1
```

## 7. `beasthunter_skin1` 的产物让查看器（spine-cpp）**访问冲突崩溃**（2026-09-17 登记）

> ⚠️ 定位这个 bug 要反复跑渲染器：**每轮都在子进程里跑，且先用
> `tools/mem_probe.ps1` 量内存**（见 `工具链与命令.md` 0.5 的硬规矩）——
> 大产物走 JSON 路径能吃到 10 GB+，并行会直接把整机拖死。

### 现象

用户在查看器里打开 `beasthunter_skin1` 的产物"动不了"——实际是**渲染进程直接崩**：

1. **不是 `.skel` 写错**：把 `.skel` 拿掉、只留 JSON，一样崩。

   deform 帧长 —— **全部通过**；JSON 里也没有重复键。

   （`BR_BeastHunter_NS1` 与 `BR_BeastHunter_NS1_BG_Only`，guid 同为 `eb0e35f0…`），
   产物里的槽位来自两边子树（`parts` 32 个）。
