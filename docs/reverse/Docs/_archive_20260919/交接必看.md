## 3. 铁律（违反过的都出过事）

1. **只用磁盘静态资源**转（prefab / Mesh / Material / Sprite / `.anim` /
   AnimatorController）。Unity 编辑器或运行时导出的 PoseFrames / PlayFrames /
   StaticMeta **只做校准，不进成品**。
2. **内存红线：不量内存不许并行。** 重活先用 `tools\mem_probe.ps1` 量
   **进程树峰值**（它连子进程一起数，超 `-LimitMB` 直接杀）；
   **同时跑的峰值之和 ≤ 10 GB**（本机物理内存只有 15.8 GB）。
   - 查看器渲染走 **JSON 路径** + 大产物 = **10 GB+**（draculina 245 MB JSON 实测 >11.6 GB）；
     同一份产物只要 **`.skel` 在**（查看器优先读二进制）就只有 **0.6~0.8 GB**
     ⇒ **大产物先 `python tools\write_all_skel.py <产物根>`**。
   - 单角色转换最重 1.26 GB；`convert_all --jobs N` 是内存乘数，大角色只开 1~2。
   - Unity 批处理（`ModelInspect.All` ≈1.84 GB）同时只跑一个，绝不与渲染/转换并行。
   - **"连续加载很多骨架"的脚本会线性泄漏**：`_scratch\q3_audit_load.py` 跑到第
     25 个角色时进程已 **10.3 GB**（spine-cpp 不回收）⇒ 必须 `--max 5` 分片 + 先量内存。
   - **大产物一律走 `.skel`，别开 JSON**：实测 `draculina_skin1` 的 JSON 一加载就
     **10.5 GB**（`.skel` 路径只有 ~0.1 GB）；`q3_audit_load.py` 用 `--bin` 才是 skel 路径。
3. **看图片不要用 `Read`**：用多模态看图（或先 `_scratch\crop_zoom.py` 裁切放大）。
4. **只挑一个主力角色做回归**（默认 audrey）：动公共代码后重导 audrey，
   要求"静态检查四项全 0"；改了关键几何/顺序时再和 `_scratch\_sanity*` 对比
   **逐字节一致性**。
5. **真值先体检再用**（见 `总正确转化.md` 第 6 节）：场景实例可能被改过、
   采样可能越过 clip 时长、状态首帧有过渡、同名孪生节点会让对账假报警。
6. 长任务别 `sleep` 干等；不要随手全量重转（先出清单、局部验证、再全量）。

## 5. 最容易踩的七个坑（都是真踩过的）

| 坑 | 症状 | 正解 |
| --- | --- | --- |
| 查看器读大 JSON | 渲染进程 `0xC0000005` / 整机卡死 | 先 `write_all_skel`；渲染前用 `mem_probe.ps1` 量 |
| **一打开就崩、连帧都不出** | `SpineData` 构造期 `0xC0000005`（不用 GL 也能复现） | 先跑 `_scratch\q3_audit_load.py <产物根>` 定位角色；多半是**多页 `.atlas` 没有尾换行**（规则 15），重导即可 |
| 把"场景真值"当游戏 | 一堆"不一致"其实是我们对、场景被改过 | 先跑 `_scratch\scene_flags.py` + `scene_vs_prefab.py` 体检 |
| 拿状态第一帧当真值 | `xxx t=0` 各种对不上 | Unity 侧采 t≈0.05~0.1 起；t=0 的 PoseFrames 顶点本身可能是垃圾 |
| 同名孪生节点 | 某部件"一直不显示"或"永远显示" | 对账按"同一路径有没有任一可见"判；曲线在 Unity 只绑第一个 |
| 曲线路径是哈希 | 某角色表情/手完全不动 | `path_0x…` = CRC32(相对宿主路径)，主文档 3.36 已还原 |
| **对账工具自己写错字段** | 成品明明一致，工具却报"某件被隐藏" | 先拿官方口径交叉核（`tools\check_clip_visibility.py` + 至少第二个真值源）；2026-09-19 的"draculina 8 件"就是 `vis_truth_check.py` 把 attachment 帧读成 `k["attachment"]`（实际是 `name`）造出来的 |

## 7. 两个"杀手锏"（判断不了时先想到这两条）

> 只要出现"**报告说和 Unity 不一样，但我们自检全绿**"，就不要再猜 —— 用下面两条里

### 7.1 C# 脚本导 **Unity 运行时数据**（Play 模式）

两个现成脚本，都在 Unity 工程 `Assets\Editor\` 下，**菜单一键跑、参数硬编码**：

| 脚本 | 导什么 | 入口 |
| --- | --- | --- |
| `PlayRefShot.cs` | **参考帧**：PNG + 相机参数 + 同帧逐渲染器数据（路径/显隐/排序/世界顶点/包围盒） | 菜单 `Tools/2DModel/运行时采样/参考帧（带相机）…`（参数在 `PlayRefShotPlan`） |
| `ExportDrawOrder.cs` | **渲染顺序**：排序键（含**反射读到的 `Renderer.sortingKey`**）+ **成对隔离渲染实测的"谁盖谁"** | 菜单 `Tools/2DModel/运行时采样/渲染顺序导出：按内置清单开始`（参数在 `ExportDrawOrderPlan`） |

要点：**Play 模式**（`-batchmode` 进不了 Play）；日志 `D:\VB\Unity2Spine\info\_logs\play_sample.log`；
产物在**统一导出根** `D:\VB\Unity2Spine\info`（`info\_refshot_<角色>\`、`info\_draworder_<角色>\`、
`info\Data\…`、日志 `info\_logs\play_sample.log`）；
`ExportDrawOrder` 默认 `TouchMode="observe"`（**不改场景**，等游戏自己显示再采，
所以画面就是直接 Play 的样子），读结果用 `python tools\read_draworder.py <目录>`。

### 7.2 **反汇编（IDA）做源码校对**

Unity 没源码，但引擎算法能从 DLL 里读出来：

| 东西 | 路径 |
| --- | --- |
| 库 | `_reverse\UP2022.dll.i64`（IDA 8.3 数据库 + 同名 `.pdb`） |
| 查询器 | `tools\ida_q.py`（`info/names/strings/xrefs_to/disasm/decompile/funcs_at/calls/bytes_at`） |
| 跑法 | `idat64.exe -A -L"_reverse\ida_q.log" -S"tools\ida_q.py" "_reverse\UP2022.dll.i64"`（请求/结果放 `_reverse\req_*.json` / `res_*.json`） |

坑：多数符号地址是**跳转桩**，`decompile` 出 `JUMPOUT(x)` 要用 `x`（约 `ea+3`）再解；
跑完把 `idat64` 收掉。已用它定过：**排序比较键**（`RenderObjectSorter` @`0x180440CC5`）、
`renderQueue ≤2500/>2500` 两套列表分开排、`SetBoundCurveFloatValue` 的 case 编号、
`GenerateSpriteOutline`。地址清单见 `docs\渲染顺序_反汇编研究.md` 与
`docs\_archive_20260917\` 下两份逆向笔记。
