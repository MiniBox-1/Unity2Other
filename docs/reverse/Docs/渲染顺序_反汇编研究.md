## 1. 找到的关键符号

| 符号 | 地址 | 作用 |
| --- | --- | --- |
| `ForwardShaderRenderLoop::RenderObjectSorter<0>::operator()` | **0x180440CC5** | 前向渲染**排序比较器**（透明/不透明各一个模板实例） |
| `RenderObjectSorter<1>::operator()` | 0x180440AD2 | 同上（另一档） |
| `BuildRenderObjectData` | **0x18042D1A3** | 把渲染器填成 56 字节/条的排序记录 |
| `CompareSortingGroupData(GlobalLayeringData&, GlobalLayeringData&)` | 0x1804317D0 | 键完全并列时再比一层"全局分层数据" |

## 2. 比较器按什么排（0x180440CC5）

反汇编逐条读（`r10` = 记录 A，`r11` = 记录 B，记录 56 字节）：

```asm
mov edx, [r10+2Ch]      ; A 的第一顺位键（u32，来自 GlobalLayeringData）
cmp edx, [r11+2Ch]
setnbe al / setb r8b / sub eax,r8d
jz next                 ; 相等才看下一个键
shr eax,1Fh             ; 否则返回 (A < B)
next:
movzx eax, word ptr [r10+10h]   ; 第二顺位：u16
cmp ax, [r11+10h]  / setl al
next2:
movss xmm0,[r10+20h] / movss xmm1,[r11+20h]   ; 第三顺位：float 深度
ucomiss → 不等就返回深度比较
相等 → call CompareSortingGroupData(r10+2Ch, r11+2Ch)   ; 第四顺位
       之后还有 [rdi+1Ch]（u16）、[r10+8]/[r10+Ch]（u32）等稳定化字段
```

**比较键顺序**：

1. `u32 @ 记录+0x2C` —— `GlobalLayeringData`（打包的"层 + 顺序"）
2. `u16 @ 记录+0x10` —— 16 位量（记录里存的是 **renderQueue**）
3. `f32 @ 记录+0x20` —— 到相机的**深度**
4. `CompareSortingGroupData()` —— 键并列时再比"全局分层数据"
5. 之后还有若干稳定化字段（u16/u32），保证排序确定

方向：`less(a,b)` 返回 `a < b` ⇒ **键小的先画（在下层）**，与"order 大的在上"一致。

## 3. 记录怎么填（BuildRenderObjectData，0x18042D1A3）

关键几行（Hex-Rays 原文 + 标注）：

```c
v32 = v7;                     // 透明列表
if ( v30 <= 2500 ) v32 = a1;  // ← renderQueue ≤ 2500 进**不透明**列表，否则进**透明**列表
...
v36 = *(_DWORD *)(*(_QWORD *)(v26 + v45) + 340i64) << 20;                    // 高 20 位 = 层索引
*(_DWORD *)(v35 + v34 - 48) = v36;                                          // 记录+8
if ( (*(_BYTE *)(*(_QWORD *)(v26 + v45) + 336i64) & 2) == 0 )
    *(_DWORD *)(v35 + v34 - 48) = v36 | (*(_DWORD *)(v37 + 8) >> 1) & 0xFFFFF;  // 低 20 位 = 顺序>>1
...
*(_WORD *)(v35 + v34 - 40) = v30;            // 记录+16 = renderQueue（u16）
*(float *)(v35 + v34 - 24) = v8;             // 记录+32 = 深度（float）
*(_DWORD *)(v35 + v34 - 12) = v42;           // 记录+44 = GlobalLayeringData 的低 32 位
```

三个可操作的观察：

1. **不透明 / 透明是两套列表**（按 `renderQueue <= 2500` 分流），各自排序、各自绘制；
   跨这两类的先后由**队列**决定，而不是 sortingOrder。
2. 打包键里"顺序"那部分被 **`>> 1`**（不是原样），层索引占高 20 位。
3. 比较器第一顺位（记录 `+0x2C`）来自 `GlobalLayeringData` 表
   （`[rendererEntry+192] >> 12` 当索引，条目 28 字节）。

## 4. 数据侧：我们的模型被推翻在哪

用 `Assets\Editor\ExportDrawOrder.cs` 的成对隔离实测（18:2x 那批，
**101,520 条强证据**，votes≥20）核对 `(sortingLayer, sortingOrder, -深度)`：

| 结果 | 条数 |
| --- | --- |
| 规则说对（键更大 ⇒ 在上） | 52,925 |
| **规则说反** | **17,794** |
| 键完全相同（真并列，只能看 tie-break） | 363（dfs↓ 218 / dfs↑ 145） |

排除项：`sortingLayer` 全是 `Default(0)`；材质 `renderQueue` 全是 `3000`；
类型分布也不是"sprite 与 mesh 走不同通路"（违反里 14,051/18,157 是
SkinnedMeshRenderer 之间）。反例集中在"**低 order 盖住高 order**"，例如
`parts_003_shoes_R_skinned`(order 3) 盖住 `parts_finger_L_S_01`(order 19)，531 票。

⇒ 要么**比较器第一顺位那个 u32 不是我们从 `Renderer.sortingOrder` 读到的数**，
要么**实测在那些对上不可靠**。两者都得用"Unity 自己的键"来定案。

## 6b. 补充（2026-09-18）：`m_SortingOrder` 本身是**可动画**的

前面 1~6 节讲的是"**给定一帧**的排序规则"；但真值还揭示了另一半：
**`m_SortingOrder` 会被动画曲线改**（引擎侧就是 `SetBoundCurveFloatValue`
的 case 10 = SortingOrder），所以同一个件的先后**逐帧会变**。

实测（`_draworder_draculina_skin1__PECS_Draculina_NS1`，状态 `Tep_1`）：

| 件 | n0050 的 order | n0650 的 order | 我们 `partsMeta` 的静态值 |
| --- | --- | --- | --- |
| `Part_Finger_R11_5` | 43 | 5 | 5 |
| `Part_Finger_R21_4` | 42 | 4 | 4 |
| `Part_Finger_R31_3` | 41 | 3 | 3 |
| `Part_Finger_R41_2` | 40 | 2 | 2 |

我们把排序烘成**静态 slot 顺序**（`multiDrawable` 默认关，`_static_info.json` 里
`relativeLayers.multiCount = 69` 即"98 件里 69 件会变层级"），于是"手指该压在上面"
的那些帧画反了 —— 用户看到的"抓绳子的动作没有"就是这个。

**待修**：把逐帧排序写成 Spine 3.8 的 **`drawOrder` 时间轴**
（`animations.<动画>.drawOrder`），而不是给 69 个件开多 drawable。
（详见 `历史问题与修复.md` 第 9.2 节、`交接与核查.md` 第 7 节）

## 6c. 再往下挖一层（2026-09-18 晚）：比较器里还有 **3 级我们没建模的 tie-break**

> ⚠️ **本节最后那条"落地规则（父子对反转）"已作废**（2026-09-18 深夜）：
> 它依据的"实测"其实是 `tieGroups[].empiricalOrder` —— 脚本里**拓扑排序的默认
> 填法**（无约束时按 idx 升序），**不是测量值**。banshee 手那条真因是
> **同网格多渲染器的骨骼表不一致**，跟排序无关；见
> [`历史问题与修复.md`](历史问题与修复.md) 第 10 节。下面这段比较链本身仍然有效。

用 `tools\ida_q.py` 把 `RenderObjectSorter::operator()` @`0x180440CC5` 整段拉出来
（产物 `_reverse\res_tie.json`，命令与 8.1 节同），比较链是**七级**：

| 序 | 字段 | 写法 | 我们的模型 |
| --- | --- | --- | --- |
| 1 | `[obj+0x2C]`（u32：层 + sortingOrder） | `cmp / setnbe / setb / sub`（升序） | ✅ 规则 12 前半 |
| 2 | `[obj+0x10]`（u16：renderQueue） | `cmp ax / setl` | ✅（≤2500 / >2500 两套列表） |
| 3 | `[obj+0x20]`（float：depth） | `ucomiss`，`jp/jnz` 时**继续往下比** | ✅ 深度 |
| 4 | `CompareSortingGroupData(...)` | `call`；非 0 直接返回 | ✅ SortingGroup |
| 5 | **`[entry+0x1C]`（u16）** | `movzx/cmp/setb al` | ❌ **没建模** |
| 6 | **`[obj+0x0C]`（u32）→ 不等再比 `[obj+0x08]`（u32）** | `cmp/jnz` | ❌ **没建模** |
| 7 | **`[obj+0x1C]>>1`（u16，低位像 flag）** | `shr/shr/cmp` | ❌ **没建模** |

**为什么这条重要**：banshee 的成对实测（`_draworder_banshee_skin1__Size_root_531be451`，
`PairScope="tie"`）出现**互相矛盾的两组**，而这两组在**所有可导出字段上完全相同**
（`sortingOrder` / `rendererPriority=0` / `renderQueue=3000` / `sortKey` / `tieKey` /
`sortingGroup*` / `camDepth` 都一致）：

| 对 | 关系 | enum / dfs | 实测（先画→后画） | 结论 |
| --- | --- | --- | --- | --- |
| `parts_Eye_normal` vs `parts_Eye_Sleep` | 不同骨骼下的**兄弟** | 3/22 vs 7/27 | `[Sleep, normal]`（`a-above-b` 票 89:0） | **index 小的在上** |
| `parts_Mouth_normal` vs `parts_Mouth_angry` | **兄弟** | 11/33 vs 13/36 | `[angry, normal]` | **index 小的在上** |
| `parts_Hand_R` **父** vs **子** | **直系父子** | 66/196 vs 68/198 | `[父, 子]` | **子在上**（与规则 12 相反） |

⇒ 决定先后的是第 5~7 级那几个**内部字段**（我们导不出来），但**等价规则可以直接用实测**：

> **同一 `sortingOrder` 内：兄弟按原规则（DFS 小的在上）；直系父子对反过来 ——
> 父先画、子后画（子在上）。**

这解释了 `banshee_skin1` 手腕"一条硬边黑线 + 手心被盖住"：我们按原规则把**父**画在上，
Unity 是**子**在上 ⇒ 手背/阴影件压住了手心。

**后续**（记进 `现状与问题.md`）：① 把"父子对反转"实现进 `slot_key_with_rank`；
② 想彻底对齐第 5~7 级，需要把 `RenderObjectData` 的 `+0x1C`/`+0x0C`/`+0x08` 也读出来
（要在 `ExportDrawOrder.cs` 里用反射/内部 API，属"能用实测就不必做"的备选）。

新版导出（`ExportDrawOrder.cs` 用反射读 `Renderer.sortingKey`）跑出来：**79/79 个渲染器
都读到了**，值形如 `0x80001000 + sortingOrder`（本批全是 Default 层 ⇒ 前缀恒定）。

拿它当第一顺位核对实测（`banshee_skin1` + `cerberus_skin3`，40 份导出）：

| 规则 | 符合 / 违反 |
| --- | --- |
| `(unitySortingKey, -深度)` | **5,012 / 0** ✅ |
| `dfs↑`（枚举/DFS 升序，**旧实现**） | 2,443 / 2,612 ❌ |
| `dfs↓` | 2,612 / 2,443 ❌（单看也不对，因为没带 order/深度） |

剩下 43 条是"**键 + 深度完全相同**"的真并列，其中 **36 条**是
**枚举/DFS 序小的在在上面**（7 条相反）。
